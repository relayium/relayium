# Relayium link v1 (authoritative)

`link/1` is one encrypted WebRTC connection to one peer carrying **two**
ordered, reliable SCTP lanes: a file lane and a text lane. It is the only
realtime transport a current Web build composes, and a peer that does not
announce exactly `link/1` is unreachable from it — there is no legacy lane left
to fall through to.

**What "encrypted" does and does not claim.** A link is *commit-reveal-complete*:
each side proved the key it revealed matches the commitment it made first, and
AEAD authenticates every frame after that. That is the precise claim, and it is
deliberately not written as "authenticated". Neither the commitment nor the AEAD
establishes that the peer is the *intended* person — only an out-of-band
comparison of the six-digit SAS does, and displaying the SAS is **optional and
off by default** in every shipped client (see `relayium-handshake-v1.md` and
`relayium-text-v1.md`, which make the same distinction). Everywhere below,
"authenticated link", "authenticated leave" and "authenticated rebuild" mean
*keyed by the secrets that commit-reveal produced*, never *identity-verified*.

This document is the wire contract. It was written from the shipped
implementation, not from an earlier plan:

- `web/src/lib/peer-caps.svelte.ts` — the roster hello, the cadence, admission.
- `web/src/lib/webrtc-core.ts` — generations, `establish`, deadlines, capture,
  `authPayload`, `linkLeavePayload`, the channel-tuple contract.
- `web/src/lib/webrtc.ts` — `connectLink` (commit-reveal) and
  `connectResumeLink` (authenticated transport rebuild).
- `web/src/lib/peer-link.svelte.ts` — link lifecycle, request/busy/leave,

- `web/src/lib/transfer.ts` / `text-wire.ts` — the two lanes' codecs.

  lane state machines, consent ordering, bounds.
- `apps/RelayiumKit/Sources/RelayiumKit/Realtime/LinkProtocol.swift` — the
  second implementation of this same vocabulary.

Layers defined elsewhere and **not** restated here except where `link/1` narrows

## 1. Capability

### 1.1 The name

The capability string is exactly `link/1`, matched with byte equality. `link/2`,
`LINK/1`, `text/1` and a peer that never announced are all equally *not this
protocol* and are all equally unreachable. There is no prefix match, no version
range and no case folding.

A conforming client MUST NOT announce a capability for which it has no
registered handler. `text/1` names the retired single-lane conversation
transport; the Web withdrew it precisely because announcing it invited peers
onto a lane the page could no longer open. An untruthful capability is worse
than a missing one — it is the one input a peer is entitled to act on.

### 1.2 What each client announces

| Client | Roster hello |
|---|---|
| Web (current) | `["link/1", "preupload/1"]` |
| Apple native (current) | `["text/1", "link/1"]` |
| A `link/1`-only client (e.g. Android) | `["link/1"]` |
| Any client where link mode is inactive | `[]` (still a hello) |

The two shipped hellos are **not** in a subset relation in either direction. The
shared contract is narrower and exact: both name `link/1`, and that is the one
capability either side may act on.

`preupload/1` (file-lane frame kind 12) rides with `link/1` and can never be
announced without it. It is a separate capability with its own derived key and
its own forward-only receive sequence; an unannounced kind is a **hard error**,
so a speculative kind-12 frame kills the whole transfer rather than degrading.
A client that does not implement it announces nothing for it and will never be
sent one.

### 1.3 The roster hello

Transport: a bare signalling frame `{"caps": [<string>, ...]}` addressed to one
peer, sent over the rendezvous socket (`relayium-signaling-v1.md` §Sequence step
4). It is **not** a WebRTC signal and carries no generation tag; handlers that do
not recognise it ignore it.

The roster level is the authoritative announcement, and it must be, because a
capability that arrives with a connection's own SDP arrives too late: a peer
predating `link/1` treats **any** inbound offer as a file transfer, waits for a
manifest that never comes, and fails it as a stall.

Cadence — one value for every room and every client, pinned by
`capability.retry` / `capability.settleSeconds` in the fixture:

- `LINK_CAPS_ANNOUNCE_ATTEMPTS = 3`
- `LINK_CAPS_RETRY_INTERVAL_MS = 1500`
- Peer settle window before concluding "this peer is legacy": **5 s**.
- Therefore the last attempt lands at most `(3-1) * 1500 ms = 3 s` after the
  first (`capability.lastAttemptSeconds`), strictly inside the 5 s window with
  room left to be acted on. Raising either constant alone breaks the other side.

Rules:

- Announcing is driven **only** by the roster gaining a peer this client has not
  greeted, by the bounded retry tick, and by this page becoming the current one.
- Hearing from a peer **retires** what is owed to it and MUST NOT produce an
  announcement. Answering a hello with a hello is an unbounded ping-pong; the
  one-way rule is structural, not a convention.
- A peer that answers is retired immediately; a peer that leaves the roster is
  dropped; a room change forgets every id.
- The Web sends the first attempt immediately on roster gain (landing at 0,
  1.5 and 3.0 s); the Apple clients send theirs on the first tick (1.5, 3.0 and
  4.5 s). Both are conforming: what the contract fixes is the count, the
  interval and that every attempt lands inside the peer's settle window.

### 1.4 Parsing a hello

Peer-authored input on an untrusted channel. Parse leniently, record
conservatively, and never throw out of the signalling dispatch loop:

- A non-object, or an array, is **not a hello** — leave any earlier
  announcement standing.
- A missing `caps` field, or a `caps` that is not an array, is **not a hello** —
  same. `{"relayRtt":{...}}`, `{"caps":"text/1"}`, `{"caps":3}` and
  `{"rename":"x"}` are all frames we do not understand, not peers with no
  capabilities.
- A `caps` array is a **snapshot**, not an additive grant. `["text/1","link/1"]`
  followed by `[]` revokes `link/1`.
- Non-string entries inside a well-formed array are dropped; the remaining
  strings are recorded.
- Announcements are pruned when their peer leaves the roster. A reconnecting
  peer is issued a fresh id by the hub, so nothing stale is inherited.

### 1.5 A link offer as an announcement

A frame on the `link` generation is itself proof that its sender speaks
`link/1` — nothing else composes one. It may stand in for a hello that never
arrived, but **only for a peer that has said nothing**. It MUST NOT overrule a
peer that has already stated its wire. Fixture: `capability.provenLink`.

### 1.6 `caps` is a hint, never a security input

The signalling relay sees every frame. It can strip `caps` (link mode is
disabled — pure denial of service) or forge it (a link is offered to a peer that
cannot hold one — also denial of service). It can never cause plaintext to be
sent: every key on this transport is **derived** from the commit-reveal, never
negotiated, so no code path downgrades to cleartext.

`caps` is deliberately **outside** the resume-auth signed payload (§4.4).
Implementations MUST NOT extend that payload.

## 2. Channels

### 2.1 The exact tuple

```
LINK_CHANNEL_LABELS = ["relayium", "relayium-text"]     // primary first
```

This is a **tuple**, not a set and not a list. The empty list, the one-element
`["relayium"]` (the retired single-lane transport), a reversed pair, a duplicate
and an extra lane are each rejected at construction, before any
`RTCPeerConnection` exists and before the first signal goes out.

- The **initiator** opens both through DCEP, in tuple order.
- The **responder** collects them by exact label from `ondatachannel`; arrival
  order is irrelevant. A channel whose label is not in the tuple, or a duplicate
  of one already collected, is closed on its own — the required set may still
  arrive normally.
- The connection is ready only when **both** labelled channels are `open`.

A link whose text lane never opened is **not a degraded link**. It is a link
that cannot honour `link/1`, and it MUST fail rather than be used.

Both lanes are reliable and ordered. Both are read as binary
(`binaryType = "arraybuffer"`). SCTP low-water mark for send pacing: 8 MiB.

### 2.2 Pre-attachment capture

An SCTP stream can deliver data before its sibling has finished DCEP, and on an
authenticated rebuild those frames belong to codecs that already exist and whose
sequences must stay continuous. A conforming client therefore captures inbound
frames on **both** lanes from the moment each channel is collected, and replays
them into the lane owners in arrival order once both are attached.

```
LINK_CAPTURE_MAX_BYTES = 256 * 1024        // combined across BOTH lanes
```

Deliberately far smaller than the file flow-control window: pre-attachment
traffic has not reached a content-consent state yet. It is one maximum encrypted
manifest plus lifecycle overhead.

**Overflow is fail-closed, never silent truncation.** A dropped admitted frame
is exactly what the receiving codecs cannot survive: the peer counted it, so
skipping it strands the sequence permanently. On overflow the link fails.

### 2.3 Handler ordering

Attach the lane's receive handler **before** emitting any consent byte on that
lane. A message dispatched on a DataChannel with no listener is dropped and there
is no replay. This is a wire invariant in both directions and on both lanes; see
§6.2 and §7.1.

## 3. Deterministic role

```
linkRole(selfId, peerId) = selfId < peerId ? initiator : responder
```

- `selfId` / `peerId` are the opaque room ids the hub issued on `welcome` and in
  the roster. The current server issues 16 lower-case hex characters.
- The comparison is a plain lexicographic ordering of those strings. For the
  ASCII ids in use, code-unit ordering and byte ordering agree; an implementation
  MUST use one of those and MUST NOT use a locale-aware or
  canonical-equivalence collation.
- It is total. A self-collision — impossible in practice — resolves to
  `responder` rather than trapping.

Without this rule two users pressing at the same moment produce two SDP offers
into one pair of lanes. The **smaller** id offers; the larger id asks and waits.

The role is fixed for the life of the authenticated link. An authenticated
transport rebuild (§8) reuses the establishment role and MUST NOT recompute it,
so a rebuild can never turn two peers into two offerers.

Fixture: `capability.role` — both orders, so a client cannot be correct in only
the half of pairings it happens to test.

## 4. Signalling

### 4.1 Generations

Every WebRTC signal carries a generation tag so concurrent connections on one
signalling link ignore each other's SDP.

Inbound classification, in this precedence order:

```
resume   if signal.resume === true
link     else if signal.link === true
text     else if signal.text === true
file     otherwise
```

`resume` outranks `link`: a signal carrying both is a rebuild, never an
establishment.

The inbound vocabulary is deliberately **wider than what can be constructed**.
`file` is the untagged generation a deployed older peer still sends and `text`
is the retired single-lane one. A conforming `link/1` client builds neither, but
MUST still be able to *name* them — a tag it could not classify would fall
through to `file` and be answered as a legacy transfer, which is the exact
failure the tags exist to prevent.

Constructible generations: `link` and `resume` only. There is no untagged
default.

### 4.2 The frames

| Frame | Shape | Direction |
|---|---|---|
| Link request | `{"link":true,"linkRequest":true}` | larger id → smaller id |
| Offer | `{"link":true,"sdp":{...},"commit":"<b64>","caps":[...]}` | initiator → responder |
| Answer | `{"link":true,"sdp":{...},"commit":"<b64>","caps":[...]}` | responder → initiator |
| Reveal | `{"link":true,"reveal":{"key":"<b64>","nonce":"<b64>"}}` | each side, once |
| ICE | `{"link":true,"ice":{...}}` | both |
| Busy | `{"link":true,"busy":true}` | either |
| Leave | `{"link":true,"leave":true,"auth":"<b64 44>"}` | either |
| Resume offer/answer/ICE | same as above with `"resume":true` and `"auth"` | §8 |

A link request carries **no** `sdp`; that absence is part of recognising it.

`commit` and `caps` ride every SDP offer and answer as the per-connection
confirmation of the roster hello, so both sides know them before the channel
opens (`relayium-handshake-v1.md`).

### 4.3 `busy`

`{"link":true,"busy":true}` means "I cannot take a link right now" — a
requeue/retry signal, not a refusal of the peer. It MUST carry the generation tag
of the exchange it refuses, or the initiator filters it out and waits out its
own connect timeout instead of failing fast.

A conforming client answers `busy` when, and only when:

- another peer already holds its single link, is being established, or is being
  requested;
- a resource-admission policy declines this peer;
- a late offer arrives from a peer whose own request already timed out on this
  side (answered rather than black-holed, so the sender retries);
- a held offer's chase-frame budget overflowed (§5.4).

Receiving `busy` while connecting fails that establishment immediately.

### 4.4 The exact bytes a tag covers

Two payloads, both hand-serialised. A tag is only meaningful over stable bytes,
and neither `JSONEncoder` on Darwin nor a general-purpose Kotlin JSON library
guarantees this key order or this escaping. Serialise these by hand.

**Resume/ICE signalling payload** — an explicit field list, in this order:

```
{"sdpType":<string|null>,"sdp":<string|null>,"candidate":<string|null>,
 "sdpMid":<string|null>,"sdpMLineIndex":<number|null>,"usernameFragment":<string|null>}
```

rendered with no whitespace. The list is explicit rather than "the whole signal"
so that adding a field to the signal cannot silently change what an existing tag
covers. `caps` is deliberately outside it. `usernameFragment` rides an ICE
candidate init and is covered even by clients that never emit one.

**Link-leave payload** — a different string, deliberately not the one above:

```
{"kind":"link-leave","from":"<selfId>","to":"<peerId>"}
```

- A leave carries no SDP and no ICE, so the resume payload would render one
  constant string for the whole life of a link — a tag with no direction,
  replayable in either direction once observed.
- `kind` makes this string unreachable from the resume payload, whose output
  always begins with `sdpType`, so a signature over one can never be mistaken
  for a signature over the other.
- `from`/`to` are the room peer ids as each side knows them, so a relay that
  reflects a leave back at its sender verifies the reversed tuple and fails.
- Cross-link replay needs no nonce: the key is the link's `resumeAuth`, which a
  later link never shares.

**String escaping** for both payloads is JavaScript `JSON.stringify`'s, exactly:

- `"` → `\"`, `\` → `\\`
- U+0008 → `\b`, U+0009 → `\t`, U+000A → `\n`, U+000C → `\f`, U+000D → `\r`
- any other scalar below U+0020 → `\u00XX`, lower-case hex, zero-padded to four
- **everything else is emitted raw**, including U+007F DELETE, the C1 range,
  U+2028 LINE SEPARATOR and U+2029 PARAGRAPH SEPARATOR, and astral characters
  (as their UTF-8 encoding — no `\uXXXX` surrogate pairs)

Fixture: `link.authPayload` and `link.linkLeavePayload`, each with its exact
rendered string and that string's UTF-8 bytes, including control, quote,
backslash, U+2028/U+2029 and astral cases.

### 4.5 The tag itself

```
tag = base64(HMAC-SHA-256(resumeAuth, utf8(payload)))
```

- `resumeAuth` derivation: `relayium-crypto-v1.md`. Both sides derive the same
  value because the input session secrets are sorted before hashing.
- base64 is **standard RFC 4648 with padding** — not URL-safe, not unpadded.
- A 32-byte HMAC encodes to exactly **44** characters
  (`LINK_AUTH_TAG_LENGTH = 44`). Checking the length before any base64 decode or
  HMAC also bounds the work a hostile signal can buy.
- An absent or malformed tag is a **failure**, never a pass. There is no
  "unauthenticated is acceptable" branch; one would make the whole binding
  optional at the attacker's choosing.

### 4.6 Leave: exact shape, and why

A leave signal carries exactly the three keys `link`, `leave`, `auth` and
**nothing else**. Recognise it by that shape, before anything cryptographic runs.

The allow-list is the point, not a formality. A leave rides the `link`
generation, which means an establishment in flight for the same peer sees it too
— that filter is by generation, not by message kind. A smuggled `commit` would
be recorded by the handshake, a `caps` array would reach the capability
registry, a `busy` would fail a connecting link, and `sdp`/`ice` would be handled
outright. Requiring exactly `{link, leave, auth}` makes the signal inert
everywhere except the leave handler — and makes that property testable.

Refuse: any extra key; a missing key; `auth` that is not a string; `auth` whose
length is not exactly 44; `link` or `leave` not `true`; a non-object payload.
Key order in the received JSON object is irrelevant.

Verification order — every cheap check runs **before** the HMAC:

1. exact shape (above);
2. a current link exists, and it is with this sender;
3. the link's status is `open` or `interrupted`;
4. the per-link attempt budget is not spent;
5. only then, verify `HMAC(resumeAuth, linkLeavePayload(from = sender, to = self))`.

```
LINK_LEAVE_MAX_ATTEMPTS = 8      // HMACs ever spent on inbound leaves, per authenticated link
```

One verification at a time; the rest of a burst is dropped without spending
budget, so a flood costs one HMAC rather than one per message. The budget resets
when a new authentication step begins (a new link), **not** when a transport is
rebuilt under the same keys.

A leave that does not verify is dropped **in silence**. Answering would tell a
signalling relay which peer holds a live link. Losing a genuine leave entirely is
safe by construction: it degrades to exactly the recovery-window behaviour of a
peer that dropped off the network.

Sending a leave is best effort and reserved for an **explicit user disconnect**.
An idle close, a room reset, a peer leaving the roster and page teardown all stay
silent. Signing must not block or throw into the teardown that follows it.

## 5. Establishment

### 5.1 Sequence

1. Both sides know each other's roster hello and each computes `linkRole`.
2. **Larger id**: sends `{"link":true,"linkRequest":true}` and waits. It repeats
   every `LINK_REQUEST_RETRY_MS = 3000` and gives up at
   `LINK_REQUEST_TIMEOUT_MS = 30000`.
3. **Smaller id**: creates *both* channels in tuple order, then
   `createOffer` / `setLocalDescription`, and sends
   `{sdp: offer, commit, caps, link: true}`.
4. **Responder**: records `peerCommit` (and `caps`) **before** handling the SDP,
   sets the remote description, creates and sets an answer, and sends
   `{sdp: answer, commit, caps, link: true}`.
5. **Initiator**, on the answer: it now holds the responder's commit, so it
   reveals — `{link:true, reveal:{key, nonce}}`.
6. **Responder**, on a reveal: verifies it against the recorded commit. On
   success it reveals its own key in the same turn, then derives. On failure —
   mismatch, or no commit recorded — it is a **hard error**; the channel never
   opens. Duplicate reveals (e.g. after an ICE restart) are ignored.
7. Both derive session keys and the SAS (`relayium-handshake-v1.md` step 5).
8. The link is usable only when both lanes are open **and** the peer key has been
   revealed and verified.

Step 4's ordering is load-bearing: answering an offer sends this side's commit,
and the peer's commit must already be recorded, or a reveal arriving in the same
burst has nothing to verify against.

Displaying the SAS and asking a human to compare it is **optional** and off by
default. A client that never shows it is conforming; a client that requires it
before opening the lanes is not implementing this protocol's default.

### 5.2 Deadlines

Every one of these is a real constant of the shipped implementation. An
implementation may be stricter but MUST NOT be unbounded anywhere.

| Bound | Value | Scope |
|---|---|---|
| No-progress | 30 s | transport setup; **re-armed** by a first-time progress event |
| Setup hard cap | 90 s | transport setup; **never** re-armed |
| Candidate progress cap | 6 | remote candidates that may re-arm the no-progress timer |
| Key reveal | 30 s | from **both channels open** to a verified peer key |
| Handshake deadline | 90 s | from handshake start to a verified peer key; never re-armed |
| Link authentication | 30 s | manager-level bound on the same window |
| Link request | 30 s total, 3 s retry | the larger id waiting for an offer |

"Progress" is keyed, and the two kinds of key behave differently — this is a
place where the shipped source's own comment overstates what its code does, so
the exact behaviour is written out here:

- **SDP and connection-state progress is deduplicated by identity.** The keys are
  the literal strings `sdp:offer` / `sdp:answer` and `state:<state>`, so a
  re-offer of the same type, or a state that flip-flops back to one already seen,
  buys no second extension.
- **ICE progress is a bounded COUNT, not a deduplication.** The key is
  `ice:<n>` where `n` is a counter incremented on each `addIceCandidate` the
  connection *accepted*. The candidate string is never compared, so the **same
  candidate sent six times does extend the deadline six times.** What bounds it
  is the count: after six accepted additions no further candidate extends
  anything, and candidates past the sixth are still added to the connection.

The ceiling on the whole setup is therefore the 90 s hard cap, which is never
re-armed by anything; the no-progress timer can be pushed at most six times by
ICE plus once per distinct SDP type and connection state.

Both transport timers are cleared the instant the channels open; the key-reveal
window starts *there* rather than at the beginning, so a setup that spent 80 s
legitimately progressing does not then get a fresh 30 s, and one that opened
instantly is not left waiting out the overall deadline in silence.

A transient `disconnected` triggers an ICE restart. Only the **initiator** drives
it, and only **once**, so a genuinely dead path fails fast instead of looping
offers.

### 5.3 One link at a time

A conforming client owns at most one `link/1` at a time. Every phase — an
outstanding request, an establishment in flight, an offer held pending a relay
decision, an established link, a rebuild — binds the client to exactly one peer.
An arrival from a **different** peer during any of those is answered `busy`. An
arrival from the **same** peer is idempotent: it joins the phase already in
flight rather than starting a second one.

Specifically: a duplicate offer from the peer whose offer is already held is
**dropped**, not held again — the establishment is built from the first one, and
applying a second is an error the transport would reject.

### 5.4 Holding an offer

A client that must wait on some local decision before answering an offer (the
Web waits for its room's relay agreement) MUST hold the offer and everything
that chases it, in arrival order, rather than answering late or dropping the
chase frames. Everything on the `link` generation from that peer — the commit,
the answer, and above all the trickled ICE candidates — belongs to the
establishment about to be built from it, and the transport that will read them
does not exist yet.

```
LINK_HELD_SIGNAL_MAX = 64        // chase frames held for one offer
```

Past it the held offer is **abandoned and the peer told `busy`** — never
truncated. A link built from a prefix of its own candidates is not the one the
peer is establishing, and a silent truncation is indistinguishable from a healthy
connection that simply never finishes.

### 5.5 Codec identity

One link owns exactly one instance of each nonce-bearing codec for its lifetime:

- file sender, file receiver (session keys, one global sequence)
- text sender, text receiver (derived text keys, one per-direction sequence each)
- pre-upload sender, pre-upload receiver (derived pre-upload keys) — only in a
  client that announces `preupload/1`

A new batch, a reopened conversation and an authenticated transport rebuild MUST
reuse these objects. Constructing a replacement restarts a counter under a key
that has already sealed frames at those sequence numbers, which is nonce reuse
under AES-GCM.

## 6. The file lane (`relayium`)

Frame bytes, kinds, sealing, the manifest and the integrity chain are
`relayium-realtime-wire-v1.md`. This section defines what `link/1` adds: the
total frame partition, the lifecycle bytes, and the obligations a receiver takes
on.

### 6.1 The frame-class partition

Every byte string arriving on the file lane lands in **exactly one** class. The
partition is total by construction, it runs on every inbound message before any
consent, and it is allocation-free.

| Class | Test | Note |
|---|---|---|
| `lifecycle` | length **exactly 1** and the byte is one of the five below | |
| `ack` | length **exactly 13** and `frame[0] == 6` | shape only; the *value* is a separate decision |
| `resumeRequest` | length ≥ 5 and `frame[0] == 5` | **including a payload that does not parse** |
| `resumeStart` | length ≥ 5 and `frame[0] == 4` | plaintext realignment announcement |
| `protected` | length ≥ 5 and `frame[0] ∈ {1, 10, 7, 11, 8, 3, 2}` | fed to the AEAD receiver in wire order |
| `unroutable` | anything else | **fail the lane** |

Consequences that are easy to get wrong:

- A kind-6 frame of any length other than 13 is **unroutable**, not protected.
  It is not an ACK — `parseAck` refuses it — and it must not fall through into
  the protected stream either.
- A frame shorter than 5 bytes that is not a one-byte lifecycle control is
  unroutable: below the header there is no kind to dispatch on at all.
- Kind 5 is `resumeRequest` **even when its payload is malformed**. That
  distinction is the one the lane needs: a malformed resume request is control it
  must fail closed on, never bytes to route into the protected stream.
- The two legacy kinds 3 (`BATCH_LEGACY`) and 2 (`DONE_LEGACY`) are classed
  `protected` **deliberately**. The receiver is the single place that turns them
  into a loud "peer is running an older version" error; a demux that swallowed
  them here would downgrade a version mismatch into silence. They are never
  parsed.
- `unroutable` **fails the lane**. On an ordered channel it is either corruption
  or a peer speaking a protocol this build does not have, and skipping one frame
  the peer counted strands the receiver's sequence permanently.
- A client that announces `preupload/1` demuxes kind 12 **by kind alone, ahead of
  the file receiver**, including a frame too short to be a valid one. A client
  that does not announce it classifies kind 12 as `unroutable`, which is exactly
  what the Apple clients do.

Fixture: `link.frameClass`.

**What the fixture can and cannot prove.** `link.frameClass` pins the *routing
answer* for one frame in isolation. The Web has no single exported total
classifier — it demuxes inline in `mixed-file-session.svelte.ts` — so
`web/src/lib/link-protocol-vectors.test.ts` composes the answer out of
`controlKind` / `isBatchAbort` / `parseAck` / `isResumeReq` and also asserts each
of those predicates individually.

That composition is **written by the test, not by the product**, and passing it is
therefore *not* evidence that the live session demux routes the same way. It does
not exercise ordering against the receive chain, the consent gate that refuses
protected content before ACCEPT, the resume-realignment gate, the pre-upload
discriminator that must run ahead of the file receiver, or lane failure on an
unroutable frame. A port MUST NOT treat a green frame-class suite as conformance
of its receive path.

An implementation that *does* own a total classifier (Swift's
`linkFileFrameClass`, and the Kotlin port's equivalent) must drive these vectors
through **that function**, and must additionally drive its real receive state
machine — the actual demux, in wire order, across the consent and realignment
gates — before claiming this section is implemented.

### 6.2 Lifecycle bytes

A lifecycle control is **exactly one byte**. A longer frame that merely starts
with one of these values is a protected frame or a malformed one, and reading it
as consent is how a peer would get a batch accepted without a user ever
answering. The length check is the whole control, not a formality.

| Byte | Name | Direction | Meaning |
|---|---|---|---|
| `0xfe` | ACCEPT | receiver → sender | this batch is consented to |
| `0xff` | REJECT | receiver → sender | this batch is refused, or an accepted one stopped |
| `0xfd` | COMPLETE | receiver → sender | the whole batch arrived **and verified** |
| `0xf9` | BUSY | receiver → sender | the lane is occupied; requeue, not a refusal |
| `0xf8` | BATCH_ABORT | **sender → receiver** | ordered barrier retiring exactly this batch |

`0xfe`/`0xff` are the same two bytes the text lane uses; the DataChannel **label**
is what scopes their meaning to a file batch rather than a conversation.

### 6.3 Batch lifecycle

Sender:

1. `BATCH_ENC` at the sender's current sequence (0 on a fresh link), fragmented
   as `BATCH_PART` … `BATCH_ENC` if the manifest does not fit one message.
2. Wait for `ACCEPT` / `REJECT` / `BUSY`. On timeout, emit `BATCH_ABORT`.
3. Per file: the logical chunks, each as `CHUNK_PART` … `CHUNK`, then
   `DONE_ENC`.
4. Honour the flow-control window and SCTP backpressure throughout (§6.5).
5. Wait for `COMPLETE`.

Receiver:

1. Feed the manifest frames in wire order **even while busy** — the encrypted
   manifest is the consent prompt.
2. Validate the manifest (`relayium-realtime-wire-v1.md`; `MAX_FILES = 1000`,
   name and path ≤ 1024 UTF-8 bytes each, sizes and their running total
   non-negative safe integers) and sanitise names (§6.6).
3. Prompt, or apply the platform's automatic-accept policy.
4. **Attach the receive handler, then** send `ACCEPT`.
5. Enforce `seq == expected` on every protected frame.
6. ACK durably-written bytes (§6.5, §9).
7. Send `COMPLETE` only after **every** file's chain hash has verified.

**Protected file content that arrives before consent is a hard lane failure.**
The receiver MUST NOT decrypt a `CHUNK` or `DONE_ENC` frame while the batch is
still awaiting a decision, even transiently — the lane's nonce state is
abandoned together with the channel instead. The manifest is the sole exception,
because it *is* the consent prompt.

**ACCEPT is an activation signal, not evidence of human consent.** Automatic
ACCEPT and human-gated ACCEPT are both conforming and indistinguishable on the
wire. An implementation MUST NOT read a received ACCEPT as "someone looked at
this".

### 6.4 BATCH_ABORT

`0xf8` is an **ordered sender→receiver barrier** that retires exactly one batch.

- It travels on the same ordered queue as the protected frames, so it cannot
  overtake a frame it is meant to follow. Handling it out of band could release
  the lane while an earlier slow write is still pending.
- It resets **only** the per-file integrity accumulator and any partial
  fragment buffer.
- The **global nonce sequence deliberately continues across it.** A batch abort
  is not a key event.
- The lane stays usable for the next batch, and the **text lane is untouched**.
- Cancelling MUST NOT be implemented as "close the PeerConnection". That is the
  legacy behaviour `link/1` replaced, and it destroys the conversation and every
  later batch along with the cancelled one.

After an abort the receiver discards its partial destination (§9) and both sides
may start a fresh batch on the same link at the continuing sequence.

### 6.5 Flow control and fragmentation

```
CHUNK_SIZE        = 192 * 1024     // the LOGICAL unit; a constant of the wire
MANIFEST_MAX_BYTES = 200 * 1024    // compared against payload + 16 (the GCM tag)
CHUNK_OVERHEAD    = 5 + 16
MIN_PIECE_BYTES   = 4096
FLOW_WINDOW       = 8 * 1024 * 1024
FLOW_ACK_INTERVAL = 512 * 1024
```

`CHUNK_SIZE` is the unit the integrity chain hashes, the unit the receiver writes
and checkpoints, and therefore the unit a resume point must land on. **It does not
vary with the connection.**

What does vary is the per-message ceiling. SCTP negotiates it, and per RFC 8841 a
peer that advertises no `a=max-message-size` means **64 KiB**:

```
piecePlainBytes(maxFrameBytes) = min(floor(maxFrameBytes) - CHUNK_OVERHEAD, CHUNK_SIZE)
```

and a result below `MIN_PIECE_BYTES` is a named error, not a transfer that crawls.
Against a real browser the negotiated ceiling is routinely 65 536, giving 65 515
plaintext bytes per message — so **every** logical chunk fragments. `CHUNK_PART`
(10) and `BATCH_PART` (11) are required on send *and* receive from the first
build; they are not a later optimisation.

Fragmentation rules:

- Each piece is sealed separately and **burns its own sequence number**.
- The last piece of a logical unit carries the terminating kind (`CHUNK` /
  `BATCH_ENC`); the rest carry the PART kind.
- An empty plaintext still yields exactly one (final) frame; a plaintext that
  divides evenly yields no trailing empty frame.
- The receiver reassembles the plaintext **before** hashing or parsing, so the
  hash chain, the checkpoint grid and the resume contract stay expressed in
  `CHUNK_SIZE` regardless of how the bytes were carried.
- Interleaved PART kinds (a `CHUNK_PART` while a `BATCH_PART` is buffered, or
  vice versa) is an error.
- The accumulator is bounded: `CHUNK_SIZE` for chunk parts, `MANIFEST_MAX_BYTES`
  for manifest parts. **The bound is checked before the "nothing buffered"
  shortcut**, because it bounds the logical unit, not the fragmentation — a peer
  that skips the PART kinds and sends one oversized authenticated terminal frame
  is the cheapest way to hand a receiver an arbitrarily large plaintext to hash
  or JSON-parse before any consent.
- A `DONE_ENC` with pieces still buffered is an error: a file cannot end in the
  middle of a chunk.

Flow control:

- The sender stays at most `FLOW_WINDOW` bytes ahead of the latest ACK, and also
  respects SCTP `bufferedAmount`.
- The receiver ACKs cumulative durably-written bytes at least every
  `FLOW_ACK_INTERVAL`.
- ACK frame: `[0x06][uint32 BE 0][Float64 BE bytesWritten]`, exactly 13 bytes.
  Fixture `ackHex` pins `bytesWritten = 1 048 576` as
  `06000000004130000000000000`.
- A received ACK is clamped: it advances only if it is **strictly greater than**
  the current value **and no greater than the bytes this attempt has actually
  emitted**. A delayed, duplicated or forged cumulative ACK therefore cannot open
  a later batch's whole window. ACK carries no batch identifier; this clamp is
  what stands in for one.

### 6.6 Names

Filenames are attacker-controlled on both transports and land on the card a user
makes a trust decision from.

At the **single decode entry point** — manifest parsing — strip, from `name` and
from **each `/`-separated segment of `path`**:

- Unicode `Bidi_Control`: U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069.
- C0, DEL and C1: U+0000–U+001F, U+007F–U+009F.

Per segment, not over the whole string, so the `/` separators survive and the
directory structure is not flattened. `path` must be sanitised as well as `name`:
the display card shows `name`, but the bytes land at `path`, and sanitising only
the former puts a disguised name on disk while showing a clean one.

Fixture: `sanitizedNames`, against a manifest whose raw names deliberately embed
U+202E and U+0007.

## 7. The text lane (`relayium-text`)

Frame bytes, key derivation, the strict-UTF-8 rule and the session bounds are
`relayium-text-v1.md`. What `link/1` adds is that this lane is **mandatory** and
that its lifecycle has two bytes of its own.

### 7.1 Lifecycle bytes

Exactly one byte, same rule and same reason as §6.2.

| Byte | Name | Meaning |
|---|---|---|
| `0xfa` | REQUEST | initiator → recipient: open a conversation |
| `0xfe` | ACCEPT | recipient → initiator: handler attached, content may flow |
| `0xff` | REJECT | recipient → initiator: declined |
| `0xfb` | END | either: this conversation is over |

`0xfd` COMPLETE belongs to the file lane and has **no meaning here**.

The recipient MUST attach its frame handler **before** sending ACCEPT, and the
initiator MUST NOT send a content frame before receiving one. Both halves are
load-bearing in opposite directions: a message dispatched with no listener is
dropped with no replay, and a peer that sends before ACCEPT has its frames
dropped undecrypted — which is the safe direction, and is also the peer breaking
its own session, since its sequence is consumed and the next frame is rejected
as out of order.

### 7.2 Content frames

```
[0x09][seq: uint32 BE][sealed(textKey, seq, utf8Bytes)]
```

- `seq` is **per direction, from 0**, monotonic, never rewound, and completely
  independent of the file lane's counter. Keys are the derived `textSend` /
  `textRecv` (domain `relayium-text-v1\0`, 17 bytes including the NUL; see
  `relayium-crypto-v1.md`), never the session keys.
- Payload is the message's UTF-8 bytes and nothing else — no envelope, no id, no
  timestamp.
- Decode strictly: invalid UTF-8 is a **hard error**, never U+FFFD.
- Minimum frame length is 21 bytes (5-byte header + 16-byte tag). A frame that
  begins with `0x09` but is shorter is malformed and fails the lane.
- `TEXT_MAX_BYTES = 65 536`, measured on the plaintext in UTF-8 bytes. One
  message, one frame, **no chunking** — an oversized message is refused *before*
  sealing, so no nonce is burned and the conversation survives.
- On a connection whose negotiated ceiling is 65 536, the effective plaintext
  limit is `65 536 − 21 = 65 515`. Handing an oversize message to `send()`
  instead kills the channel and takes the whole session with it.
- There are no acknowledgements and no resume on this lane.

Fixture: `text.frames` — three bodies including a multibyte/astral mix and one
whose whitespace must survive byte for byte.

### 7.3 Demux and unknown frames

The text lane's demux is, in order: one-byte lifecycle control → content frame
(`length ≥ 21 && frame[0] == 9`) → everything else.

The Web treats a frame that begins with `0x09` but is too short as a **hard text-lane
failure**, and silently ignores a frame beginning with any other byte. This is
deliberately *less* strict than the file lane's total partition (§6.1), because
this lane carries no sequence a dropped unknown frame could strand. An
implementation MAY fail closed on any unrecognised text-lane frame; it MUST NOT
route one into the AEAD receiver.

A text-lane failure MUST NOT take the file lane with it, and vice versa.

### 7.4 Session bounds

Receiver-enforced. They bound resource use rather than defining the wire.

| Bound | Value |
|---|---|
| session messages | 500 |
| session bytes | 4 MiB |
| inbound rate | 20 burst, 5/s |
| send buffer | 1 MiB |
| idle | 10 min |
| rendered history | 200 |

## 8. Recovery and resume

### 8.1 What a link survives

An established link's DataChannels are a transport separate from the signalling
socket. Losing the signalling socket does not end the link; losing the transport
does not, by itself, end the *authentication*.

When the transport dies, a client MAY hold the link — keys, SAS and all six
codecs untouched — and rebuild a transport under it:

```
LINK_RECOVERY_WINDOW_MS = 90 000
LINK_RECOVERY_RETRY_MS  =  1 500
```

- Only the **establishment-role initiator** drives the rebuild. The responder
  runs no driver at all; it answers the initiator's authenticated offer. There is
  therefore no rebuild glare and no new signal type.
- A relayed link derives a shorter window from the time left on its TURN
  credential, so the driver can never still be re-offering under an expired one.
  A window of zero means "not holdable" and the link fails immediately rather
  than showing a recovery that cannot succeed.
- The rebuilt transport reuses the exact session keys, SAS and codec objects.
  Only the connection and the two channel objects change.
- The `failed`-then-`closed` pair a dying connection emits is **one** gap, not
  two.

### 8.2 The rebuild is authenticated, and that is the only thing holding it

A rebuild runs on the `resume` generation and **does not** re-run commit-reveal.
Possession of the link's `resumeAuth` is what proves the offer came from the same
peer — and a signalling relay, which sees every SDP in the clear, cannot produce
it.

- Every resume SDP and every resume ICE candidate carries `auth` over the
  resume payload of §4.4.
- The receiving side verifies the tag **before** allocating a peer connection or
  beginning ICE, and before committing the single rebuild slot to that offer.
- An offer that is not for this link's peer, not for an interrupted link, or not
  signed by this link's keys is **dropped in silence**.
- `auth` is not optional on this generation. An unauthenticated resume is a
  second connection anybody on the signalling path could offer into a session
  that has already been verified.
- One inbound resume offer at a time may hold the rebuild slot, so two offers
  arriving in one burst cannot both start a connection into the same lanes.

### 8.3 Sequence realignment

After a gap the file lane's receive sequence is unaligned. Exactly one plaintext
frame is acceptable until the peer says where it resumed:

- `RESUME_START` (kind 4, plaintext, sender→receiver):
  `{"index":<int>,"offset":<int>,"seq":<int>}` in that key order. It consumes no
  sequence number and announces the sequence the **first** resumed protected
  frame will carry.
- `RESUME_REQ` (kind 5, plaintext, receiver→sender): `{"index":<int>,"offset":<int>}`
  in that key order — the last point the receiver durably holds.
- All three numbers must be **non-negative safe integers**. A negative `offset`
  would make the sender slice a file from its end; a huge `index` would make it
  skip every file and idle silently.
- A resume point must be **aligned**: `offset == size` or
  `offset % CHUNK_SIZE == 0`. The chain hash is defined only at chunk boundaries,
  so an unaligned point can only come from a peer that is not following this
  protocol or from a relay-injected frame — and honouring one would make the
  sender skip the bytes between the request and the next boundary.
- A resume point must be **in range**: `index < files.length` and
  `offset <= sizes[index]`.
- **The receive sequence may skip forward but MUST NEVER move backwards.**
  Rewinding it would make an old ciphertext valid again under the same key and
  sequence number. Frames that were emitted and lost simply burn their numbers.
- Partial fragments held from the dead transport are discarded; the sender
  restarts from a whole-chunk boundary.
- A `RESUME_START` on a lane that is **not** awaiting realignment is a hard
  error, as is a second one, as is one whose `index`/`offset` do not match the
  receiver's own durable checkpoint. That narrowness is what keeps a forged
  plaintext frame from being a free sequence jump at any moment the peer chooses.
- On an idle direction with no batch in flight, the only valid announcement is
  the origin `{index: 0, offset: 0}`.
- A resumed batch never re-sends `BATCH_ENC`: consent was given once and the
  manifest is already authenticated.
- Chunks are hashed from byte 0 even when they are not sent, so the per-file
  `DONE_ENC` still covers the whole file and a connection that renegotiated a
  different message size still agrees on the hash.

### 8.4 A first-stage client may refuse recovery

Recovery is a **capability of an implementation, not a term of the wire**. A
conforming client MAY implement none of §8, on these conditions:

- It must still **recognise and refuse** `resume`-generation signals, kind 4 and
  kind 5, fail-closed. It must not misroute them into the protected stream, and
  it must not answer them.
- On transport loss it ends the link truthfully and lets the user start a fresh
  session. It must not present an unrecoverable link as `interrupted`.
- It must not claim resume support in any user-facing or machine-readable
  surface. There is no capability string for recovery, so the only honest signal
  is the absence of a claim.

A client that refuses recovery is **not** speaking a partial dialect: every byte
it does emit is `link/1`, and its peer's rebuild attempts simply go unanswered
until that peer's own recovery window expires — which is exactly the behaviour of
a peer that walked away.

## 9. Storage and durability obligations

These are not UI rules. They are what makes the flow-control ACK meaningful and
what makes `COMPLETE` a claim rather than a hope.

1. **An ACK is a durability claim.** `ackFrame(n)` asserts that `n` cumulative
   bytes of this batch are *durably written*, not that they were appended to a
   buffer. A sink that ACKs on buffer-append breaks the sender's pacing contract:
   the sender races to the end, its buffer empties, it declares itself done, and
   the receiver is still writing a large in-memory backlog it then misreads as a
   mid-transfer drop. Advance the ACK only after the bytes have reached the file
   descriptor.
2. **Checkpoint only on the grid.** Nothing is written, hashed, parsed or
   checkpointed from a partial logical chunk, so the durable state a resume can
   restart from stays exactly on the `CHUNK_SIZE` boundary, with the chain hash
   and the byte count agreeing.
3. **`COMPLETE` only after verification.** Send `0xfd` only once every file's
   recomputed chain hash has matched the hash its `DONE_ENC` carried.
4. **Never present a partial or failed save as success.** A per-file success
   requires a locally durable, verified save; a batch success requires
   `COMPLETE`. Text has no delivery receipts at all and must never claim one.
5. **Cancellation cleans up.** Two claims, and they are not the same strength.

   *Normative for every implementation:* `BATCH_ABORT` retires exactly one batch
   and leaves the lane, the sequence and the text lane usable (§6.4), and a fresh
   retry of the same batch succeeds on the same link. A partially received file
   must never be reported as a success (item 4).

   *A first-stage Android acceptance requirement, NOT a verified property of the
   shipped Web and Apple clients:* after a cancel, no batch **document** is left
   at the user-chosen destination. Android reaches it in two phases. Before any
   export begins, staging is app-private and a cancel has nothing to clean up in
   the user's tree. Once verified files start exporting, every identity the batch
   creates is recorded at creation, classified there as file or directory, and a
   cancel — or a provider write/flush/close failure mid-copy — deletes exactly
   the recorded file documents, never anything found by name and never anything
   that existed before the batch. A recorded **directory** is removed only where
   the provider offers an atomic empty-only delete; SAF's `deleteDocument` is
   recursive and offers none, so batch-created directories are left standing
   there rather than risking a user file placed inside them, and the client
   reports the cleanup as incomplete instead of claiming full removal. The
   existing clients have their own platform semantics under which files already
   completed earlier in the batch may legitimately remain, and this document does
   not retroactively make those non-conforming.

   In no case does cleanup extend beyond documents this batch itself created. An
   implementation MUST NOT delete or overwrite a pre-existing user file, and MUST
   NOT touch anything outside the destination this batch wrote.
6. **Discard callbacks from stale transports.** A dead connection's terminal
   callback must not tear down a newer one, and a write that completes after its
   transport was replaced must not publish success against the live link.
7. **`DONE_ENC` and the manifest are encrypted for a reason.** The manifest is
   file names and sizes; `DONE_ENC` carries the file's **chained** digest —
   `h = SHA-256(h || chunk)` over `CHUNK_SIZE` logical chunks starting from 32
   zero bytes, **not** a plain SHA-256 of the file's contents. It is still a
   stable per-file fingerprint that a DTLS-level observer could compare against a
   candidate file it also chained the same way, which is why it is sealed rather
   than sent in the clear.

   The obligation is about **transit and server-visible surfaces**, not about the
   local UI: neither value may travel in plaintext, be written to logs, telemetry
   or crash reports, or be handed to any party that is not an endpoint of this
   link. An endpoint that has legitimately decrypted the manifest *must* be able
   to show the file names — that is the receive prompt the user makes a trust
   decision from (§6.6). Displaying a decrypted name locally is required
   behaviour, not a leak.

## 11. Non-goals and refusals

A conforming `link/1` client MUST refuse, fail-closed, and MUST NOT attempt to
interpret:

- Frame kinds 2 and 3 — a peer on an older wire. Never parse them; report a
  version mismatch.
- Frame kind 12 unless it announced `preupload/1`.
- Any frame kind not in §6.1's partition.
- An SDP offer from a peer whose announcement is not exactly `link/1` — with
  the one exception §1.5 defines and which this list does not override: a `link`
  generation offer from a peer that has announced **nothing at all** is itself
  the announcement, and may be answered. A peer that has stated an incompatible
  snapshot (`[]`, `["text/1"]`, `["link/2"]`) is refused, and an offer never
  overrules it.
- A `resume`-generation signal without a verifying `auth`.
- A leave signal that is not exactly `{link, leave, auth}` with a 44-character
  tag that verifies over the correct direction.
- A `RESUME_START` that was not asked for.

And it MUST NOT:

- fall back to any plaintext path;
- rewind any receive sequence;
- construct a second codec for a link whose keys already sealed frames;
- extend the resume-auth signed payload;
- treat `caps` as a security input;
- read `ACCEPT` as evidence a human approved anything;
- close the peer connection as a way of cancelling one batch.

## 12. Known ambiguities

Recorded here rather than resolved, because resolving any of them changes shipped
behaviour and belongs to its own scoped task.

1. **`RESUME_START` with `seq ≥ 2^32`.** `relayium-realtime-wire-v1.md` states
   such a frame is "malformed and rejected outright rather than accepted and left
   permanently unmatchable". The shipped Web receiver only requires a
   non-negative safe integer that does not move the sequence backwards, so a
   `seq` of 2^32 is *accepted* and then matches no frame's on-wire uint32, and
   the transfer stalls until a watchdog. The doc is stricter than the code. A
   third implementation should implement the **documented** rule (reject at or
   above 2^32) — it is a strict subset of what the Web accepts and cannot break
   interop — but the divergence is real and the Web-side check is missing.
2. **Lone surrogates in a tag payload.** `authPayload` is rendered with
   JavaScript `JSON.stringify` semantics, which escape an unpaired surrogate as
   `\udXXX` (well-formed `JSON.stringify`). A Swift `String` cannot hold a lone
   surrogate at all, so the Swift port has no defined behaviour for one. The
   values that reach these payloads in practice — hub peer ids and
   browser-generated SDP — are ASCII, so this is defensive only; but two
   implementations do not currently agree on it. The fixture records the case and
   flags it.
3. **First-attempt timing of the capability hello.** The Web sends attempt 1
   immediately (0 / 1.5 / 3.0 s); the Apple clients send it on the first tick
   (1.5 / 3.0 / 4.5 s). Both land inside the 5 s settle window and both are
   conforming under §1.3, but the fixture's `lastAttemptSeconds` measures the
   span, not the absolute schedule, so it does not distinguish them.
4. **Text-lane strictness.** §7.3's asymmetry (fail on a short kind-9, ignore an
   unknown first byte) is what the Web does. It is safe, but it is a weaker rule
   than the file lane's, and a future tightening would be a behaviour change on
   both existing clients.
