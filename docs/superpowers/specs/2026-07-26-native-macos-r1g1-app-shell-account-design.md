# Native macOS R1-G1 — app shell + account — design

Date: 2026-07-26
Status: approved (design), pending implementation plan

## Background

R1-A through R1-F are merged. `RelayiumKit` implements the whole client stack —
`Crypto`, `StoredWire`, `Account`, `Cloud`, `Signaling`, `Handshake`,
`RealtimeWire`, `Realtime` — with 100 unit tests, three sets of golden vectors
generated by the web implementation, and a live native↔native realtime transfer
proven end to end through the production signaling hub.

The macOS app is still the two-file shell from R1-A: a `WindowGroup` rendering
`Text(RelayiumKit.sodiumReady() ? "core ready" : "core FAILED")`. Every
capability exists; none of it is reachable by a human.

R1-G was defined as one round — "macOS UI + Universal Links + distribution
(Developer ID sign/notarize/Sparkle/.dmg)". That is five independent subsystems,
which is more than one plan can hold honestly. This document decomposes R1-G and
specifies its first sub-round.

## R1-G decomposition

| Sub-round | Scope | Gated on |
|---|---|---|
| **G1** | App shell (window + menu-bar residency), login, Keychain persistence, `/api/me` + `/api/me/usage` rendering, billing opens web | nothing — **this spec** |
| G2 | Cloud transfer UI: drag in → upload → `#k=` link; paste link → download → Reveal in Finder | G1 |
| G3 | Realtime transfer UI: pairing code, SAS confirmation, progress, Bonjour discovery | G1 + two Kit contract debts (below) |
| G4 | Universal Links (`/d/*`, `/cross-network`) + user notifications | G2/G3, plus `RELAYIUM_APPLE_APP_IDS` set to `<TeamID>.com.relayium.mac` |
| G5 | Developer ID signing, notarization, Sparkle, `.dmg`, `/apps` page flip | Apple Developer Program membership |

The ordering is forced, not chosen. `POST /api/files` is registered behind
`RequireAuth` (`server/account/files.go:66`), so there is no cloud transfer to
show before there is a session — account precedes transfer.

The Kit contract debts G3 depends on, both recorded in R1-E's handoff notes:
`SignalingClient` callbacks do not arrive on the main thread, and `close()`
cannot distinguish "I closed this" from "the peer closed it", which any
reconnect logic needs. Neither blocks G1, which makes no realtime connection.

## G1 scope

**In:** app shell with both a `WindowGroup` and a `MenuBarExtra`; email +
password login; bearer token persisted in the login keychain with auto-login on
launch; account screen rendering plan, traffic and storage meters, and the usage
reset date; upgrade / manage-subscription opening the browser; logout; a startup
self-check surfacing `sodiumReady()` and `webrtcAvailable()`.

**Out, each for a reason:**

- Transfer UI of either kind — G2 and G3.
- Bonjour discovery, Universal Links, notifications — G4.
- Sparkle, signing, notarization — G5.
- **Sign in with Apple.** Listed in the round-1 scope as a macOS UX win, and it
  is, but it requires an entitlement, which requires a Team ID. It belongs to
  the first sub-round that has one, not to this one.
- Device list, transfer history. Both render existing APIs and neither is on the
  path to a working transfer; they are cheap additions to G2 once the account
  screen exists.

## Architecture

### A new `RelayiumAppKit` target

`apps/mac/Relayium.xcodeproj` has no test target, and hand-editing
`project.pbxproj` to add an XCTest target is both fiddly and fragile. Writing an
untested UI layer in a repository with 100 unit tests and three sets of golden
vectors would also be out of character for the codebase.

So the platform-agnostic layer moves into a new `RelayiumAppKit` target in the
**existing** `apps/RelayiumKit/Package.swift`, and the Xcode app target keeps
only SwiftUI views:

```
apps/RelayiumKit/Sources/
  RelayiumKit/          (unchanged — the protocol stack)
  RelayiumAppKit/       (new — @MainActor view-model layer, no SwiftUI import)
    AppState.swift          launch → restore session → route
    AccountSession.swift    login/logout/refresh state machine
    UsagePresentation.swift meters → display values
    ErrorCopy.swift         Kit error taxonomy → human strings
apps/mac/Relayium/      (SwiftUI views only)
```

`RelayiumAppKit` imports `RelayiumKit` and `Foundation`, never SwiftUI — that is
what keeps it testable under `swift test` and reusable by the iOS app in R3,
which the roadmap already plans. Views observe it; it never reaches back.

### Why the boundary sits there

`AccountClient` and `CloudClient` are structs taking `URLSession` in their
initializers, and the Kit's own tests drive them through
`Support/StubURLProtocol.swift`. A view-model layer built on the same seam is
unit-testable with no new infrastructure: construct the client with a stubbed
session, drive the state machine, assert the resulting state. No protocol
wrappers, no mock framework, no change to the Kit.

## Kit contract constraints this design is built around

The Kit is plain Swift 5 with GCD and delegates: **no `Sendable`, no
`@MainActor`, no `actor`, no strict concurrency**. Every bridging obligation is
the UI's. Five constraints shape G1 specifically.

1. **`login` returning 200 does not mean the user is logged in.**
   `LoginOutcome` is `.success(token:user:)`, `.emailUnverified(email:)`, or
   `.pendingDeletion(purgeAfter:reactivateToken:)`, and a 403 carrying
   `error == "email_unverified"` is a normal return rather than a thrown error.
   The login state machine switches on all three; "did not throw" is not a
   success test.

2. **`LoginUser` (6 fields) is not `NativeUser` (14 fields).** Only `/api/me`
   carries the billing fields. Login is therefore always followed by a
   `fetchMe`, and the two shapes stay two types — collapsing them into one view
   model would silently produce an account screen with empty plan fields.

3. **`Meter.cap == 0` means unlimited, not zero.** Every meter renders through
   `isUnlimited` before any ratio is computed. A percentage bar that divides by
   `cap` crashes or shows nonsense on exactly the plans that matter most.

4. **There is no token-expiry concept.** The only signal a stored token has gone
   bad is `fetchMe` throwing `AccountError.invalidCredentials` (401). That case
   clears the keychain and routes to login; it is a normal transition, not an
   error to display.

5. **`KeychainTokenStore.load()` is synchronous and blocking**, and the first
   access can raise a system authorization prompt. It runs inside `.task { }`,
   hopped off the main actor — never in `View.body`, never in an initializer.

Additionally, **no Kit error implements `LocalizedError`**; every
`localizedDescription` is a useless type name. `ErrorCopy` is load-bearing, not
polish: it maps `AccountError`, `KeychainError`, and a catch-all fallback to
strings a person can act on.

## Data flow

**Launch:** `AppState` starts in `.restoring`. A `.task` loads the keychain token
off the main actor. No token → `.loggedOut`. Token present → `fetchMe`, then
`fetchUsage`; success → `.ready(user:usage:)`; `.invalidCredentials` → clear the
keychain, `.loggedOut`; any other error → `.ready` is not entered, and the shell
shows a retry affordance rather than bouncing the user to a login screen that
would not help.

**Login:** email + password + a device name → `AccountClient.login`. The device
name is the Mac's user-visible computer name (`Host.current().localizedName`,
falling back to `"Mac"`), so the device list on the web reads the way the user
expects rather than showing a hostname they never chose.
`.success` → save the token, `fetchMe` + `fetchUsage`, `.ready`.
`.emailUnverified` → a screen explaining the mailbox needs checking, with a
"manage on web" link. `.pendingDeletion` → surface the purge date and the
reactivation path rather than silently logging in.

**Logout:** clear the keychain, drop all cached state, `.loggedOut`. A keychain
clear failure is logged but does not block the transition — the in-memory
session is gone either way.

**Menu-bar residency:** in G1 the `MenuBarExtra` shows connection-independent
state only (signed in as / plan / open main window / quit). It exists now so
that G3's persistent WebSocket has a home that does not require restructuring
the app; it does not open a socket in this round.

## Error handling

`ErrorCopy` owns a total mapping with an explicit fallback branch. Its shape
matters more than its contents: the realtime rounds will extend the same
function with `ConnectionError`, `HandshakeError`, `RealtimeError`,
`RealtimeSenderError`, and bare WebRTC `NSError`s, all of which arrive through a
single `((Error) -> Void)` callback. Establishing a layered `if let e = error as?
XxxError` chain with a catch-all now means G3 extends a structure instead of
inventing one under pressure.

Network failures during refresh keep the last-known-good `user` and `usage` on
screen with a staleness indicator, rather than blanking the view.

## Sandbox and entitlements

App Sandbox is enabled in G1 with three entitlements: `network.client`,
`files.user-selected.read-write`, and `downloads.read-write`. Direct download
does not require sandboxing, but `apps/` is Apache-2.0 specifically so these
clients can reach the App Store, where the sandbox is mandatory. Retrofitting it
after two rounds of UI have been built against unsandboxed assumptions costs
more than adopting it before there is anything to retrofit.

`ENABLE_HARDENED_RUNTIME` is already `YES`. `DEVELOPMENT_TEAM` stays empty and
`CODE_SIGNING_ALLOWED=NO` still governs local builds until G5.

## Testing

**Unit (`swift test`, in the existing suite):**

- All three `LoginOutcome` branches produce their distinct states.
- A 401 from `fetchMe` clears the token store and routes to logged-out.
- `cap == 0` renders as unlimited and computes no ratio.
- `ErrorCopy` is total: every known error type maps, and an unknown error still
  produces actionable text.
- Restore-on-launch with an empty store goes to logged-out without a network
  call.

All of it drives real `AccountClient` instances over `StubURLProtocol`, matching
the Kit's existing test style.

**Build:** `xcodebuild -project apps/mac/Relayium.xcodeproj -scheme Relayium
-destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build`.

**Manual, and unavoidably so:** launch the built app, sign in, see the real plan
and usage, quit and relaunch to confirm auto-login, sign out and confirm the
return to login. `KeychainTokenStore` is skipped under the SPM test host — R1-C
recorded that gap and deferred verification to the round with a real app bundle
(`plans/2026-07-24-native-macos-r1c-account.md:716`). This is that round; the
manual pass closes it. Quit and relaunch *the same build* for the auto-login
check: a sandboxed, ad-hoc-signed binary ties the keychain item's ACL to that
binary's signature, so rebuilding in between can legitimately produce a keychain
prompt or a failed auto-login and fail the acceptance test for the wrong reason.

## Prerequisites recorded for later rounds

- **G4** needs `RELAYIUM_APPLE_APP_IDS` set to `<TeamID>.com.relayium.mac` on the
  production server. The AASA handler already exists and 404s while unset
  (`server/wellknown.go`, `server/main.go:101`) — configuration only, no code.
- **G5** needs Developer ID certificates from the Apple Developer Program.
- **G2** should re-freeze the `Fixtures/account/*.json` responses against the
  current Go handlers. R1-C froze them from handlers that have since moved from
  `server/internal/account` to `server/account`; the shapes are believed
  unchanged, but "believed" is what fixtures exist to eliminate.
- **Native sign-out revokes nothing server-side.** `server/account/native.go`
  (`issueBearer`) calls `UpsertDevice` with a fresh `authx.NewID()`, so the
  `ON CONFLICT(id)` in `server/account/sqlite.go` never fires: every login
  creates a *new* device row and a *new* never-expiring `rlm_cli_…` token. The
  only revocation route, `DELETE /api/devices/{id}`, is mounted behind
  `RequireSession` (cookie-only, `server/account/handlers.go:139`), so a native
  client cannot revoke its own token — `logOut()` can only forget it. From this
  round onward every sign-out/sign-in cycle leaves a live credential and a
  duplicate device-list entry behind. The fix is server-side: a `RequireAuth`-
  mounted native logout that revokes the presented token.
- **`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` is advisory in the shipped
  configuration.** On macOS that attribute is only honored by the
  data-protection keychain (`kSecUseDataProtectionKeychain: true`); against the
  legacy login keychain, which is what `KeychainTokenStore` writes to today, it
  is effectively a no-op. The intent is right; revisit in G5, when a real Team ID
  and a keychain access group exist to make the data-protection keychain usable.
- **WebRTC is sourced from a floating `branch: "latest"`.** `Package.swift`
  depends on `github.com/stasel/WebRTC.git` by branch. The app's
  `Package.resolved` now pins a revision
  (`3bdb63fdd28982ef364e5a08f53c68730a8c87b3`), which is an improvement, but a
  floating branch as the source of the WebRTC binary in an end-to-end-encrypted
  product should become a tag before G5 ships signed builds.

## Non-goals

Nothing here changes `RelayiumKit`'s protocol modules, the wire format, or the
server. G1 adds a view-model target and SwiftUI views, and edits
`project.pbxproj` twice: once to link `RelayiumAppKit`, once to add the
entitlements file.
