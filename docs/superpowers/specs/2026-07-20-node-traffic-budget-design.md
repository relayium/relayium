# 节点流量预算 + 单文件上限提升

**日期**: 2026-07-20
**状态**: 已确认，待实现
**前置**: `2026-07-20-plan-card-and-node-storage-cap-design.md`（已上线，merge 617939f）

## 背景

上一轮给节点存储加了「剩余 × 70%」的调度余量。核查时发现两件事：

1. **中继与存储是两种独立能力，代码里已经是分开的**。中继选节点走 `turn.go:145` 的 `OnlineNodes`（`WHERE owner_type='fleet' AND last_seen_at >= ?`，完全不看磁盘），blob 放置才走 `StorageNodes`。所以一台盘满的节点仍然在中继池里，只是不再接新文件——这正是期望语义。但**没有任何测试守着这件事**，哪天有人给 `OnlineNodes` 加个存储过滤，中继能力会静默丢失且无人报警。

2. **流量侧完全没有余量**。`turn.go:151` 是 `monthlyUsed >= TrafficLimitBytes`，满 100% 才把节点踢出中继池。但流量检查发生在 ICE 建连那一刻，字节却在整个会话期间累积——一台卡在 99.9% 的节点照样被发出去，接着一个大传输能把它顶过限额一大截。

同时单文件上限要从 50 MiB 提到 1 GiB，这让上一轮的 70% 存储余量从"基本不起作用"变成"在小盘上真正生效"：

| 盘总量 | 20% 整卷保留触发 | 70% 余量触发（1 GiB 文件） | 谁先拦 |
|---|---|---|---|
| 5 GiB | 剩 1.0 GiB | 剩 **1.43 GiB** | **70%** |
| 18.3 GiB | 剩 **3.66 GiB** | 剩 1.43 GiB | 20% |
| 1 TiB | 剩 **200 GiB** | 剩 1.43 GiB | 20% |

分界线在总量约 7 GiB：小盘靠 70% 拦（防止一个 1 GiB 文件吃掉大半剩余空间），大盘靠 20% 拦。两道闸各管一段，**存储侧不需要新增任何限制**。

## 设计

### 1. 单文件上限默认值 50 MiB → 1 GiB

`main.go:103` 的 `-max-file-size` 默认值改为 `1<<30`。这是 flag/env 默认值；后台「单文件上限 (MiB)」若已在 DB 里存过值，DB 值优先（`settingOr` 的既有语义）。

### 2. 节点流量上限：全局默认 + 每节点覆盖

后台**已经**有每节点的「流量上限 GB/月」（`admin_templates.go:296`），缺的是默认值。

新增全局设置 `SettingNodeTrafficDefault`（`node_traffic_default`，字节），出厂 1 TiB，后台设置区新增输入框「节点默认流量上限 (GB/月)」。

解析规则（新增 `resolveNodeTrafficLimit`）：

| 节点 `traffic_limit_bytes` | 生效上限 |
|---|---|
| `> 0` | 该值（管理员为这台机器单独配的） |
| `0` | 全局默认值 |

**`0` 的语义从「无限」变为「继承全局默认」——这是行为变更。** 现存官方节点的该字段大概率都是 0（当前含义是无限），改完后它们会立刻获得 1 TiB 上限。这正是需求，但不是只对新节点生效。

**不引入 `-1` 之类的「无限」哨兵值**：需要放开某台机器时填一个大数（如 999999 GB）即可。多一个哨兵会让那个输入框变难懂，收益不抵成本。全局默认值填 0 则表示"所有未单独配置的节点不限流量"，保留了整体关掉的能力。

### 3. 90% 调度余量

新增常量与辅助函数，与存储侧的 `storageHeadroomNum/Den` + `usableBytes` 同构：

```go
const nodeTrafficHeadroomNum, nodeTrafficHeadroomDen = 9, 10

func usableTraffic(limit int64) int64 {
	return limit * nodeTrafficHeadroomNum / nodeTrafficHeadroomDen
}
```

**中心端**（`turn.go:151`）：本月已中继 ≥ 生效上限 × 90% 时不再把该节点发给新连接。

**节点本地**（`counter.go:28` 的 `overTraffic`）：**保持 100% 才黑洞出向流量**，不改。

这 10% 不是浪费掉的额度，而是给**已经建连的会话**吐完用的缓冲。中心端收在前、节点硬闸兜在后，与存储侧「70% 调度 / 80% 整卷硬闸」是同一个模式。若节点本地也收到 90%，那 10% 就真的永远用不到了。

**下发给节点的值必须是解析后的**：`nodeLimitsFor`（`nodes.go:53`）当前直接发 `node.TrafficLimitBytes`，要改成发 `resolveNodeTrafficLimit` 的结果，否则节点的硬闸不知道全局默认的存在，对 `traffic_limit_bytes = 0` 的节点会一直认为自己无限。

### 4. 后台展示

- 节点表「可用(70%)」列改名为**「可存储(70%)」**。`可用` 一词有歧义：盘满的节点显示「可用 0 B」会被读成整台机器不可用，实际它中继跑得好好的。
- 节点表的中继列上限位改为显示**生效上限**（解析后的值），而不是节点行里可能为 0 的原始值——否则继承默认的节点会显示 `∞`，与实际行为矛盾。
- 每节点输入框的 `title` 从「流量上限 GB/月，0=无限」改为「流量上限 GB/月，0=用全局默认」。

### 5. 补测试：盘满的节点仍在中继池

钉住「中继可用性与磁盘状态无关」这条语义：构造一台 `storage_free` 低到会被 `StorageNodes` 排除的 fleet 节点，断言它**仍然**出现在 `OnlineNodes` 结果里、且仍被 `handleICE` 发进 relays。

## 不做的事

- **存储侧不新增限制**。20% 整卷保留 + 70% 调度余量的组合已覆盖 1 GiB 单文件的场景（见上表）。
- **节点本地流量硬闸不动**（保持 100%）。
- **不为单节点「无限」引入哨兵值**。

## 已知遗留

**心跳陈旧窗口被放大 20 倍。** 节点每 30s 才上报一次剩余空间，同窗口内的多次放置看到同一个陈旧值——单文件从 50 MiB 提到 1 GiB 后，每次偏差也放大 20 倍。一台报了 3.7 GiB 剩余的节点，两个并发 1 GiB 上传都会通过中心端检查；节点本地的实时 507 会拦下超出的部分，所以**盘不会被撑爆，但用户会看到上传传到快满时失败**，而不是被路由到别的节点。这是体验问题不是安全问题，本轮不治。

**免费档额度关系**：免费档月流量 1 GiB、存储 100 MiB，1 GiB 的文件他们本就传不了。1 GiB 上限实际只对付费档有意义。

**中心端 `-blob-disk-max`**：落到 app server 本机盘的兜底路径有独立软上限，1 GiB 文件下其余量需要运维复核，不在本轮代码范围内。
