# 节点自动更新 / 卸载 / 安全性说明（设计）

日期：2026-07-22
状态：设计已确认，待实施

解决的问题：机队有十几台节点，每次发版都要逐台 SSH 登录更新，不可持续。但盲目的
「每台每天自动拉最新版」会把一个坏版本在 24 小时内推给全队。本设计让更新自动化，
同时把坏版本的爆炸半径收敛到**一台**。

---

## 1. 关键前提（不要再搞混）

**更新 ≠ 卸载。**

| | 卸载 | 更新 |
|---|---|---|
| 磁盘上的密文 | 被销毁（机器不干了） | 一个字节都不动 |
| 文件可达性 | 永久不可达 | 重启后原样继续服务 |
| 需要等 TTL 排空 | **是** | **否** |
| 中断时长 | 永久 | 进程重启，秒级 |

依据：`internal/storage/disk.go` 的 `DiskStore` 是纯文件系统——`Put` 走 tmp +
`os.Rename` 原子落盘，`Get` 直接读文件，**没有任何内存索引**。进程重启后，磁盘上
的 blob 原封不动，节点回来继续服务同一批文件。

更新真正打断的只有**在途的中继会话**和**在途的下载**，靠优雅停机（§5）解决，量级
是秒。

曾经考虑过「排空后再更新」：一台节点排空要等最长 14 天 TTL，且排空期间不能接新文
件（机队容量少一台）；16 台串行 = 一个版本铺 7 个月。**不成立，已否决。**

---

## 2. 硬约束：节点进程无法更新自己

节点以 `relayium-node` 非特权用户运行，`ProtectSystem=strict` 让整个文件系统只
读，唯一可写的是存储目录。它**写不了** `/usr/local/bin/relayium-node`。

若为自更新给沙箱开 `/usr/local/bin` 写权限，等于让一个被攻破的节点改写一个 root 会
执行的二进制——`docs/node-hardening.md` 里全部加固一笔勾销。**不做。**

因此：自更新由一个**独立的 root 更新器**完成，节点本体永远不具备更新能力。这个分离
是本设计的安全基石，不是实现细节。

---

## 3. 架构

```
┌─ relayium-node.service ───────────┐  沙箱内，非 root，零 capability
│  节点本体：TURN / 存储 / /dl       │  ← 永远无权改任何二进制
│  每次心跳成功后 touch              │
│    <statedir>/last-heartbeat       │  ← 更新器读它判断健康
└────────────────────────────────────┘

┌─ relayium-node-update.timer ──────┐  root，oneshot
│  每 10min ±5min 随机               │
│  执行 `relayium-node update`：     │
│   1. 读 /etc/relayium-node/env 拿 token
│   2. 读 state.json 拿 nodeID       │
│   3. POST /api/nodes/update-check ─┼──▶ 中央（串行队列状态机）
│   4. 不该我动 → 退出（绝大多数情况）│
│   5. 该我动 → 见 §4                │
└────────────────────────────────────┘
```

更新器**不经过节点本体**取指令，自己带 node token 调中央。好处：沙箱里的节点完全不
参与更新链路，不存在「被攻破的节点伪造一个更新指令文件」这种攻击面。

心跳协议因此**不需要**新增 `targetVersion` 字段。

## 4. 节点侧：更新与本地自救

### 更新流程（`relayium-node update`，root）

1. 向中央报告「我开始更新了，从 X 到 Y」
2. 把当前二进制复制为 `/usr/local/bin/relayium-node.prev`（root 拥有，节点用户无权碰）
3. 用 `internal/selfupdate` 下载目标版本：验 `checksums.txt` 的 ECDSA 签名（公钥编译
   在二进制里）+ 验 sha256 + 原子替换。任一步失败 → 原二进制完好，上报失败并退出。
4. `systemctl restart relayium-node`
5. **守 10 分钟**：轮询 `<statedir>/last-heartbeat` 的 mtime，要求出现一次晚于重启
   时刻的成功心跳，且服务处于 active。
6. 成功 → 上报成功，删 `.prev`。
7. 失败 → 恢复 `.prev`、重启、写 `<statedir>/failed-version`（避免撞墙循环，同一版本
   不再重试）、上报失败。

### 为什么本地自救不可省

中央控制的回滚有个根本盲区：**一台起不来的节点收不到心跳，也就收不到回滚指令**。
第 5-7 步是唯一能兜住「新二进制直接炸」的东西，且完全不依赖中央。

### 降级

`internal/selfupdate` 默认拒绝降级。仅当中央显式下发一个更低的版本号（admin 的回滚
操作）时，更新器才带 `AllowDowngrade` 执行。安全性由签名校验保证——降级目标同样必须
是官方已签名的版本。

### 开关

`RELAYIUM_NODE_AUTO_UPDATE=off`（默认 on）。关闭时 timer 不安装；已安装的话
`update` 子命令直接退出。机队与 BYO 默认一致。

---

## 5. 优雅停机

更新 = 重启 = 掐断这台节点上所有在途的中继和下载。节点需要 SIGTERM 处理：

- 停止接受新的 TURN 分配和新的 `/dl` 请求
- 等在途的结束，最长 60s
- unit 里 `TimeoutStopSec=90`

不做这个的话，每次滚动更新都会在 16 台机器上依次制造一批传输失败。

---

## 6. 中央侧：严格串行队列

### 状态：两条独立轨道

`node_rollout` 表**两行**，`track` 分别为 `fleet` 和 `byo`，各自独立推进：

| 字段 | 含义 |
|---|---|
| `track` | `fleet` / `byo`（主键） |
| `target_version` | 该轨道的目标版本 |
| `current_node_id` | 机队轨：当前正在更新/观察的节点，空表示等待下一台 |
| `byo_batch` | BYO 轨：当前批次（`10` / `50` / `100`） |
| `stage_started_at` | 当前这台（或这批）开始更新的时刻 |
| `status` | `rolling` / `halted` / `complete` |
| `halted_reason` | 停止原因，供 admin 显示 |

**BYO 轨永远不能阻塞机队轨。** 这是硬要求，不是优化：

- 两条轨道的 `status` 互不影响。BYO 轨 `halted` 时，机队轨照常接受新的
  `target_version` 并正常滚动。
- 唯一的耦合是**单向门禁**：BYO 轨的 `target_version` 只能设为机队轨已经
  `complete` 的版本。我们自己的机队先趟一遍，用户的机器才跟上。
- BYO 轨卡住时发新版本：机队轨自由滚动到新版本；BYO 轨保持 halted。等你处理完
  之后，BYO 轨可以**直接跳到最新的「机队已完成」版本**，跳过那个出问题的中间版
  本——这正是我们想要的修复前进（fix-forward）行为，而不是强迫 BYO 补做一遍坏
  版本。
- 因此 admin 里是**两套独立的控制**（各自的目标版本、暂停/继续/回滚），不是一套。

### 节点属于哪条轨

按节点的 `OwnerType`：机队节点（运营方所有）走 `fleet` 轨，用户自建节点
（`OwnerType == "user"`，见 `files.go:395`）走 `byo` 轨。

节点表新增：`update_started_at`、`update_from_version`、`update_result`
（`ok` / `failed` / `rolled_back` / `skipped`）。

### 顺序

- **严格一次一台。** 任何时刻最多一台在重启，最多一台跑着未经验证的新版本。
- **首台**：选**当前在途传输最少**的节点（心跳里已有 usage 数据），把首次暴露的代价
  压到最低。观察 **6 小时**——足以暴露内存泄漏、连接泄漏这类「跑一阵子才炸」的问题。
- **其余**：按 `hash(nodeID + targetVersion)` 稳定排序，每台观察 **30 分钟**。换版本
  重新洗牌，不会永远是同一台当炮灰。
- **机队轨 `complete` 之后，BYO 轨才能设为该版本。** 这不是容量考虑，是信任边界：
  **用户的机器不该当小白鼠**，我们自己的机队先趟一遍。见下方「两条独立轨道」——这
  是单向门禁，反方向永不成立（BYO 出问题绝不拖住机队）。
- 机队全程约 14 小时（6h + 15×30min）。

### BYO 轨不能串行

严格串行只适用于机队这种「十几台、且都是我们的责任」的规模。BYO 节点数量无上限，200
台 × 30min = 100 小时，不成立。而且一台 BYO 节点更新失败并不影响机队。

BYO 轨改为**按比例分批**：10% → 6h → 50% → 6h → 100%，同样按
`hash(nodeID + targetVersion)` 排序。停止条件改为**失败率阈值**：某一批里
`failed` + `rolled_back` 的比例超过 20%（且绝对数 ≥ 2）就 `halted` + 告警。单台失败
不停队列——BYO 机器千奇百怪，个别失败是常态，不是信号。

### 推进条件

当前节点满足全部三条才轮到下一台：

1. 上报了 `update_result = ok`
2. 以目标版本持续心跳
3. 距 `stage_started_at` ≥ 该阶段的观察时长

### 停止条件（`halted` + 告警，不再自动推进）

- 当前节点上报 `failed` 或 `rolled_back`
- 当前节点在更新后 15 分钟内失联

### 节点轮到时不在线

等 15 分钟，标 `skipped`，队列继续。该节点恢复后，中央发现它版本落后且已过它的位次
→ 立即判定 eligible，它自己会补上。

### 端点

`POST /api/nodes/update-check`，node token 鉴权：

请求：`{nodeID, currentVersion, result?}`（`result` 用于上报上一次更新结果）
响应：`{targetVersion, eligible, allowDowngrade, reason}`

`eligible=false` 时节点直接退出，这是 99% 的情况。

### admin UI

在已有的节点页（`internal/account/admin_templates.go`）加一块：

- **两块独立面板**（机队轨 / BYO 轨），各自显示目标版本、状态、进度（机队 `3/16`，
  BYO `10% 批次 12/120`），各自有独立的操作按钮
- 每台节点的版本、更新结果、失败原因
- 操作：设定目标版本 / 暂停 / 继续 / 回滚到指定版本 / **紧急发布**（跳过串行，全队立
  即更新，安全修复专用，显式二次确认）

## 7. 顺带修复：重定向前不检查在线状态

`internal/account/files.go:383` 决定是否 302 到节点时**只看它有没有
`DownloadURL`，不看它是否在线**。节点重启那几十秒里，中央仍会把下载者重定向到一台
正在重启的机器（CF 表现为 522）。

修复：重定向前加 `LastSeenAt` 在线判断（复用已有的 `nodeOnlineWindow`），不在线则回
退到中央代理。这个 bug 独立于自动更新存在，但自动更新会让它每次滚动都被触发 16 次。

## 8. 卸载

### 阶段一：排空（这里才需要排空）

节点表加 `draining` 标记：**仍服务下载，但不再接收新上传**——在 `blobfor.go:57` 的
投放查询里加一个条件。

标记后等上面的文件自然过期（机队最长 TTL 14 天）。admin 显示「这台还挂着 N 个文件 /
最早可安全卸载时间」。

**为什么必须这样**：每个文件在库里只绑定一个 `NodeID`（`files.go:285`），我们**不做
副本**。卸载一台存储节点 = 上面所有文件永久不可达。

### 阶段二：卸载脚本

```sh
curl -fsSL https://relayium.com/uninstall-node.sh | sudo sh
```

1. 停 + disable `relayium-node.service` 和 `relayium-node-update.timer`
2. 删两个 unit 文件，`systemctl daemon-reload`
3. 删 `/usr/local/bin/relayium-node` 和 `.prev`
4. 删 `/etc/relayium-node/`
5. 删状态目录 `/var/lib/relayium-node`
6. 删 `relayium-node` 用户
7. 向中央**注销**（带 node token），避免 admin 里留一个永远离线的幽灵节点

**存储目录默认不删。** 必须显式 `RELAYIUM_NODE_PURGE_STORAGE=1` 才清——里面是别人
的文件，不能让一条 curl 管道顺手抹掉。检测到存储目录非空时打印剩余数据量并要求确认。

脚本在节点仍持有文件且未排空时**警告并要求确认**（`RELAYIUM_NODE_FORCE=1` 跳过）。

### 明确不做

**blob 迁移**（把文件搬到另一台节点再改 `NodeID`）需要节点间传输、一致性处理和失败
回滚，比自动更新本身还大。排空+等待对 14 天 TTL 够用，代价是卸载一台要提前两周计
划。留作独立功能。

## 9. 安全性说明（对外）

BYO 节点和官方机队节点跑的是**同一套代码、同一套加固**，唯一差别是机器归谁。这点直
接说出来比任何形容词都有说服力。

`/guides/bring-your-own-node` 新增一节「这个脚本用 root 跑，安全吗？」，六个论点：

1. **root 只存在于安装的那几秒**——建用户、装 unit。装完进程立刻降权到
   `relayium-node`，无 shell、无家目录。
2. **列出笼子挡住了什么**（表格，从 `docs/node-hardening.md` 搬）：读不到你的 SSH 私
   钥、整个文件系统只读、上传的文件在内核层面跑不起来、提不了权。
3. **自动更新下发的只是一个版本号**，二进制由节点用编译进去的公钥验 ECDSA 签名。中
   央被攻破也变不出一个能通过验签的二进制。
4. **更新器和节点是两个进程**：有 root 的那个只做更新，笼子里的那个永远无权改二进
   制。刻意的分离，不是巧合。
5. **存的是端到端加密的密文**，节点没有密钥，连自己存的是什么文件都不知道。
6. **能关也能走**：`RELAYIUM_NODE_AUTO_UPDATE=off` 关自动更新，一行命令完整卸载。

**安装脚本结束时打印一段「刚才用你的 root 做了什么」摘要**：建了哪个用户、装了哪两
个 unit、开了哪个端口、自动更新开还是关、怎么卸载。root 执行的那一刻就给出交代，比
藏在文档里强。

工作量提示：该 guide 有 9 个语言版本的静态 HTML，这一节要翻 9 遍。内容机械，但是本
设计里最占体积的部分。

## 10. 测试

- **更新器**：httptest 假 GitHub + 假中央。覆盖版本相同不动、验签失败不替换、新版本
  起不来自动恢复 `.prev`、`failed-version` 阻止重试、降级默认拒绝 / 显式允许。
- **串行队列**：表驱动测推进与停止条件，时间注入不睡。覆盖首台 6h、其余 30min、失败
  即停、离线跳过、BYO 按比例分批、BYO 失败率阈值（1 台失败不停、超阈值才停）。
- **轨道隔离**（必测）：BYO 轨 `halted` 时机队轨仍能接受新目标版本并正常滚动；BYO 轨
  的目标版本无法设为机队轨未 `complete` 的版本；BYO 轨恢复后可直接跳到最新的机队已
  完成版本、跳过中间的坏版本。
- **排序**：同版本下顺序稳定、换版本重新洗牌、首台确实是在途最少的那台。
- **在线检查**：节点离线时不发 302、回退代理。
- **卸载脚本**：容器里跑装→卸，断言残留为零、存储目录仍在；`PURGE_STORAGE=1` 才清。
- **优雅停机**：SIGTERM 后在途请求能完成、超时强退。

## 11. 实施顺序

1. 优雅停机 + 在线检查修复（独立价值，先落）
2. 更新器子命令 + 本地自救（节点侧闭环，此时手动指定版本即可用）
3. 中央串行队列 + `/api/nodes/update-check`
4. admin UI
5. `draining` 标记 + 卸载脚本 + 注销端点
6. 安全性说明 ×9 语言 + 安装脚本摘要
