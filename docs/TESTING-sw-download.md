# 手工验证：service worker 流式下载

这份清单的目的**不是**"证明功能没坏"，而是拿到一个答案：

> **iOS Safari 到底能不能把 service worker 生成的流式响应下载成一个完整文件？**

第 2 步（流式 ZIP / 多文件）和第 3 步（实时接收路也走 SW sink）是否值得做，取决于这个
答案。所以第 4 项是整件事的目的，其余各项是它的对照组和护栏。

---

## 0. 前置：怎么把被测的东西跑起来

```bash
cd web
npm run build && npm run preview
```

**dev 模式（`npm run dev`）没有 service worker，测不了这个功能。**
`share-target.ts` 的注册被 `import.meta.env.PROD` 门住，dev 下 `navigator.serviceWorker.controller`
永远是 null，`swStreamReady()` 恒为 false，页面会一路回落到旧的内存路径 —— 看上去
"一切正常"，但你测的是回落路径，不是 SW 路径。

`npm run preview` 默认起在 `http://localhost:4173`。localhost 算安全上下文，SW 能注册。
手机真机测试需要一个 **HTTPS** 地址（SW 只在安全上下文注册，局域网 IP 上的 http:// 不算）：
用线上环境，或 `npx localtunnel --port 4173` / `cloudflared tunnel` 之类开一个临时 HTTPS 隧道。

### 准备测试文件与基准哈希

```bash
# 小文件（各项通用）
mkfile 8m /tmp/sw-test-small.bin 2>/dev/null || dd if=/dev/urandom of=/tmp/sw-test-small.bin bs=1m count=8
# 大文件（第 6 项）：300 MiB，越过 256 MiB 的内存提示阈值
dd if=/dev/urandom of=/tmp/sw-test-big.bin bs=1m count=300

shasum -a 256 /tmp/sw-test-small.bin /tmp/sw-test-big.bin | tee /tmp/sw-test-baseline.txt
```

把这两个文件用**桌面 Chrome**（发送端一律用 Chrome，排除发送端变量）通过
"离线传输 / 生成下载链接" 上传，拿到两条 `/d/<id>#k=...` 链接。记下这两条链接，
下面每一项都用同一条链接，避免每项都重新上传引入新的变量。

> ⚠️ 上传时**关掉"阅后即焚"**，否则第一项测完链接就没了。

### 每一项都必须校验内容完整性

**只看"有没有下载下来一个文件"是不够的。** 这条路径上最坏的失败不是报错，而是
"看起来成功但文件被截断 / 混入了别的字节"——用户以为下载好了，几个月后才发现视频
放不出来。那比现在的内存提示糟得多。所以每一项的判定都必须落到：

```bash
shasum -a 256 ~/Downloads/sw-test-small.bin
# 与 /tmp/sw-test-baseline.txt 里的那一行**逐字符**比对
```

手机上没有 shell，把下载好的文件通过 AirDrop / 数据线 / 再上传一次传回电脑再算哈希。
**大小相同不代表内容相同**（例如 SW 被换掉后重发了一段，长度可能凑巧对上），必须算哈希。

一个方便的比对法：

```bash
cd ~/Downloads && shasum -a 256 -c <(sed 's#/tmp/#'"$HOME"'/Downloads/#' /tmp/sw-test-baseline.txt)
# 期望每行都是 "OK"；出现 "FAILED" 就是内容损坏
```

### 怎么确认这一次走的是 SW 分支（而不是悄悄回落了）

在 DevTools Console 里下载前执行：

```js
navigator.serviceWorker.controller   // 必须非 null
```

下载开始后看 DevTools → Network，应当出现一条 `/__stream__/<token>/<文件名>` 的请求，
标记为 `(ServiceWorker)`。**没有这条请求就说明走的是回落路径，这一项作废，需重测。**
另一个信号：页面上不出现内存提示（`.memwarn`），而在旧版本里 300 MiB 一定会出现。

## 1. 桌面 Chrome —— SW 分支不该抢走原生 Save As

**怎么做**：Chrome 打开小文件链接 → 点"下载并解密"。

**期望**：弹出系统原生的"另存为"对话框（File System Access API 那条路）。
Network 里**不应**出现 `/__stream__/` 请求。

**怎么判断失败**：
- 没弹对话框、文件直接落进 ~/Downloads，且 Network 里有 `/__stream__/` 请求
  → SW 分支抢走了 Chrome，说明 `pickSaveTarget` 的分支顺序错了（SW 分支必须排在
  `showSaveFilePicker` / `showDirectoryPicker` 两条之后）。
- 哈希不匹配 → 既有的原生路径被这次改动弄坏了（回归，比新功能不工作严重得多）。

**完整性**：`shasum -a 256` 与基准一致。

---

## 2. 桌面 Firefox —— 应走 SW 流式

**怎么做**：Firefox 打开小文件链接 → 下载。先按上面"怎么确认走的是 SW 分支"确认。

**期望**：无"另存为"对话框（Firefox 没有 FSA API），文件出现在默认下载目录，
文件名是原始文件名（不是 `<token>` 或一串百分号编码）。

**怎么判断失败**：
- **下载到一个 HTML 文件**（用 `file ~/Downloads/xxx` 看，或大小只有几十 KB）
  → 请求漏到了 nginx 被 `try_files` 兜底成 index.html。这是这条路径最危险的失败。
- 文件名变成 `download` 或 token → `Content-Disposition` 没被 SW 交出去。
- 进度条走到 100% 但下载项卡在"正在下载"不收尾 → `close` 回执没收到。
- **哈希不匹配 → 判定为失败，不管文件大小对不对。**

---

## 3. 桌面 Safari —— 应走 SW 流式

同第 2 项。额外注意 Safari 会把下载放进 ~/Downloads 并可能自动解压归档
（Safari 设置 → 通用 → "下载后打开安全的文件"，测试前**关掉它**，否则 .zip/.gz
会被自动展开，你算的就不是下载下来的那个文件的哈希）。

**怎么判断失败**：同第 2 项。另外 Safari 特有的失败形态是"下载项显示完成但文件是 0 字节"
或"文件停在某个中间大小"——这两种都必须算失败并记录当时的文件大小。

---

## 4. iOS Safari —— **这一项是整件事的目的**

**怎么做**：iPhone 上用 Safari 打开小文件链接（HTTPS 地址）→ 下载。

**期望**：Safari 弹出下载确认（"下载 xxx"），确认后进入"下载项"列表，完成后
文件出现在"文件" App 的 iCloud Drive/下载 或 我的 iPhone/下载。

**怎么判断失败**（把实际现象记下来，这是本步真正的产出）：
- 完全没反应 / 只闪一下 → 隐藏 iframe 的导航被 iOS 拦了。
- 打开了一个新页面显示乱码 → `Content-Disposition` 没生效，被当成内联内容渲染。
- 下载项一直转圈不结束 → 流没收尾，或 SW 在后台被回收。
- 下载"完成"但文件被截断 → **最坏的情况**，必须靠哈希才能发现。
- 下载到 index.html → 漏到 nginx。

**完整性**：把文件从"文件" App 通过 AirDrop 传回 Mac，`shasum -a 256` 比对。
**这一步不能省。** 只要哈希对不上，第 2、3 步就不该做，第 1 步的结论是"iOS Safari 不行"。

同时记录：iOS 版本、Safari 版本、机型、是否低电量模式。

---

## 5. 安卓 Chrome —— 应走 SW 流式

**怎么做**：安卓 Chrome 打开小文件链接（HTTPS）→ 下载。

**期望**：进入 Chrome 的下载列表，完成后在 `Download/` 目录里。

**怎么判断失败**：同第 2 项。安卓 Chrome 特有的一点：它**有** `showSaveFilePicker`
的部分实现吗？没有 —— 移动版 Chrome 不提供 FSA API，所以这里应当走 SW 分支。
如果 Network 里没有 `/__stream__/` 请求，先确认 `navigator.serviceWorker.controller`
非 null，再判定。

**完整性**：文件传回电脑算哈希（`adb pull /sdcard/Download/xxx` 或数据线）。

---

## 6. 大文件（300 MiB）在 iOS Safari 上

**怎么做**：iOS Safari 打开**大文件**链接 → 下载。

**期望**：
- **不出现内存提示**（那个红框的"你的浏览器不支持流式落盘…"）。这是这一步最直接的
  用户可见效果：SW 就绪时 `canStreamToDisk(1, {swStream:true})` 返回 true，提示自然
  不触发。
- 下载成功完成，哈希与基准一致。
- 下载过程中 Safari 标签页**不崩溃**（旧路径上 300 MiB 在手机上很可能崩）。

**怎么判断失败**：
- 仍然出现内存提示 → 下载页没把 `swStream` 开关传给 `canStreamToDisk`，或 SW 没就绪
  （先查 controller）。
- 标签页被系统回收 / Safari 白屏重载 → 内存没省下来，SW 流没真正生效。
- 哈希不匹配。

大文件跑一次要几分钟，中途**不要切走 app**（那是第 11 项单独测的场景）。

---

## 7. 中途取消下载 —— 页面必须报错，不能卡死或静默失败

**怎么做**：Firefox 或 Safari 上开始下载大文件，在浏览器的下载界面里点"取消"（×）。

**期望**：
- 页面几秒内进入错误态，显示**"下载已取消，文件未保存。可以重新开始下载。"**
  （`cancelled` 文案），**不是**"密钥错误或文件损坏"。
- 错误下方有**重试按钮**，点它能重新开始一次完整的下载（再校验一次哈希）。

**怎么判断失败**：
- 页面停在某个百分比一动不动超过 90 秒 → 取消信号没传回页面，`write()` 挂死了。
- 显示"解密失败：密钥错误或文件已损坏" → 归因错了。用户被告知文件坏了，其实只是他
  自己点了取消。
- 显示错误但没有重试按钮 → 用户走进死胡同。

---

## 8. 首次访问（SW 刚注册、可能还没 claim）—— 绝不能下载到一个 HTML 文件

这是这条路径上后果最严重的失败：请求漏到 nginx，`try_files` 兜底返回 index.html，
用户拿到一个扩展名正确、内容是网页的文件。

**怎么做**（必须清干净 SW 才能复现）：
1. DevTools → Application → Service Workers → **Unregister**；
   Application → Storage → **Clear site data**（勾上 unregister service workers）。
2. 关掉所有该站点的标签页。
3. 重新打开下载链接，**立刻**（页面一出现就）点"下载并解密"，不要等。
4. Firefox / Safari 上重复（Firefox: 设置 → 隐私与安全 → Cookie 和网站数据 → 清除数据）。

**期望**：要么走 SW 流式并拿到完整文件，要么**干净回落到旧的内存路径**（大文件时会看到
内存提示）。两种都可以接受。

**怎么判断失败**：
- 下载下来的文件用 `file` / `head -c 200` 看是 HTML（`<!doctype html>`）→ **严重失败**。
  说明 `swStreamReady()` 在 SW 还没 claim 时错误地返回了 true。
- 下载下来一个 0 字节文件。
- 页面报错。

```bash
head -c 200 ~/Downloads/sw-test-small.bin | file -
# 期望：data（二进制）。出现 HTML document text 就是失败。
```

## 9. "每次都问我保存到哪"对话框开着超过 60 秒

**背景**：页面侧每一次 ack 等待有 60 秒停滞上限（`STREAM_ACK_TIMEOUT_MS`）。浏览器的
"总是询问保存位置"对话框会挡住消费方的 pull，ack 因此不来。

**怎么做**：Firefox → 设置 → 常规 → 下载 → 勾选"总是询问你要保存文件的位置"。
开始下载，弹出保存对话框后**放着不动 90 秒**，再选目录确认。

**期望**（记录实际现象，两种都算合法结果，但要写清楚是哪一种）：
- (A) 下载正常完成，哈希一致 —— 说明对话框期间浏览器仍在 pull（对话框在响应体开始
  传输之前弹出，此时流还没被消费）。
- (B) 页面在 60 秒后报错"保存到磁盘时中断：请重试。"，下载失败 —— 已知取舍，可接受，
  但要记进结论，因为这会影响开着这个选项的用户。

**怎么判断失败**（真正的失败，区别于上面两种）：
- 页面无声无息停在某个百分比，**既不完成也不报错**，超过 3 分钟 → 停滞超时没生效。
- 下载"完成"但文件被截断 → 最坏情况。

---

## 10. 下载中途暂停超过 60 秒

**怎么做**：开始下载大文件，在浏览器下载界面里点"暂停"，等 90 秒，再点"继续"。

**期望**（同样两种合法结果，记录实际是哪一种）：
- (A) 恢复后继续下载并完成，哈希一致。
- (B) 页面报错"保存到磁盘时中断：请重试。"，且有重试按钮 —— 已知取舍
  （`STREAM_ACK_TIMEOUT_MS` 的注释里明确写了这一条），可接受。

**怎么判断失败**：
- 页面永久挂在某个百分比不报错。
- 恢复后下载"完成"但哈希不匹配（丢了中间一段）—— **严重**。

---

## 11. 手机上切到别的 app 再切回来（定时器被节流）

**背景**：页面靠 10 秒一次的 `stream-ping` 心跳把 SW 拉住不让它被回收。手机上标签页
进入后台后 `setInterval` 会被大幅节流甚至暂停，心跳可能停发 → SW 被回收 → 注册表蒸发。
这是手机上最可能发生的失败方式，也是这份清单里最重要的一项（仅次于第 4 项）。

**怎么做**：iOS Safari（以及安卓 Chrome）上开始下载大文件，5 秒后按 Home 切到别的
app（或锁屏），停留 **2 分钟**，再切回 Safari。

**期望**（记录实际是哪一种）：
- (A) 下载在后台继续并完成，哈希一致 —— 最好的结果。
- (B) 切回后页面显示"保存到磁盘时中断：请重试。"并有重试按钮 —— 可接受的失败：
  用户知道发生了什么，也知道怎么办。
- (C) 下载在后台完成了，但页面切回后仍显示"正在下载 x%" —— UI 状态不一致，需要记录。

**怎么判断失败**：
- 切回后页面永久停在某个百分比，既不完成也不报错。
- 下载显示完成但文件被截断 → **最坏情况**，必须记录并让第 2、3 步停下来。

如果这一项在 iOS 上稳定失败，即使第 4 项（前台短下载）通过，这个功能对手机用户
也只在"短下载 + 不切走"的窄场景里有效，结论里必须写明这个限制。

**决策**：第 4 项与第 11 项都拿到 ✅ 才建议做第 2 步（流式 ZIP）。

第 4 项 ✅ 但第 11 项 ❌ 时，功能可以留着（比现状好），但不要在第 3 步把实时接收路
也切过来 —— 那条路的传输时间更长，切后台的概率更高。
