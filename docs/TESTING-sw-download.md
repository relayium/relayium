# 手工验证：service worker 流式下载

这份清单的目的**不是**"证明功能没坏"，而是拿到一个答案：

> **iOS Safari 到底能不能把 service worker 生成的流式响应下载成一个完整文件？**

第 2 步（流式 ZIP / 多文件）和第 3 步（实时接收路也走 SW sink）是否值得做，取决于这个
答案。所以第 4 项是整件事的目的，其余各项是它的对照组和护栏。

**这份清单最容易骗人的地方是"分不出走的是哪条路"。** SW 路径和回落到内存的路径在
很多场景下产出**完全一样的文件、完全一样的哈希**——回落路径同样能把 8 MiB 完整地交到
磁盘上。如果不主动去区分，你会给一个其实走了内存回落的场景打上 ✅，然后拿着这个错误的
结论去决定第 2、3 步做不做。所以下面第 0.3 节的"分支判定"不是可选步骤，**每一项都必须
先判出分支，再判结果**；分支判不出来的那一项，结果一律作废。

## 0. 前置

### 0.1 怎么把被测的东西跑起来

```bash
cd web
npm run build && npm run preview
```

**dev 模式（`npm run dev`）没有 service worker，测不了这个功能。**
`share-target.ts` 的注册被 `import.meta.env.PROD` 门住，dev 下 `navigator.serviceWorker.controller`
永远是 null，`swStreamReady()` 恒为 false，页面会一路回落到旧的内存路径 —— 看上去
"一切正常"，但你测的是回落路径，不是 SW 路径。

`npm run preview` 默认起在 `http://localhost:4173`。localhost 算安全上下文，SW 能注册。

手机真机测试需要一个 **HTTPS** 地址（SW 只在安全上下文注册，局域网 IP 上的 http:// 不算）。
两个办法：

- 直接用线上环境（最省事，但你测的是线上那一版代码，确认部署的 commit 是你要测的那个）。
- 开一个临时 HTTPS 隧道：

  ```bash
  # macOS: brew install cloudflared
  cloudflared tunnel --url http://localhost:4173
  # 输出里那条 https://<随机词>.trycloudflare.com 就是手机上要打开的地址
  ```

> ⚠️ **不要用 `npx localtunnel`。** 它对新访客会先插一个"确认继续"的中间页，那次导航
> 会干扰 service worker 的首次注册与 claim —— 而那恰恰是第 8 项要测的东西。用了它，
> 第 8 项测的就不是我们的代码。

### 0.2 准备测试文件与基准哈希

两个文件都用 `/dev/urandom`（**不要用 `mkfile`**：它产的是全零文件，压缩/去重/截断类的
错误在全零数据上更难暴露，两个测试文件的性质也就不一致了）。

```bash
# 小文件：8 MiB，第 6 项用
dd if=/dev/urandom of=/tmp/sw-test-small.bin bs=1m count=8
# 大文件：300 MiB，越过 256 MiB 的内存提示阈值 —— 第 4/7/10/11 项用
dd if=/dev/urandom of=/tmp/sw-test-big.bin bs=1m count=300

shasum -a 256 /tmp/sw-test-small.bin /tmp/sw-test-big.bin | tee /tmp/sw-test-baseline.txt
```

把这两个文件用**桌面 Chrome**（发送端一律用 Chrome，排除发送端变量）通过
"离线传输 / 生成下载链接"上传，拿到两条 `/d/<id>#k=...` 链接。记下这两条链接，
下面每一项都用同一条链接，避免每项都重新上传引入新的变量。

> ⚠️ 上传时**关掉"阅后即焚"**，并把有效期设长（几天），否则第一项测完链接就没了。

### 0.3 分支判定：这一次到底走的是 SW 还是内存回落

有三个信号。**桌面各项以 S1+S4 为准；手机各项以 S1+S2+S3 为准。**

**S1（必要条件，不充分）**：下载**之前**在 Console 里执行

```js
navigator.serviceWorker.controller   // 必须非 null
```

null 就一定走的是回落路径。非 null 只说明"有可能"走 SW —— 探测和真正开流之间 SW 还可能
被换掉，所以不能只看这一条。

**S2（大文件时充分）**：**内存提示不出现**。
回落路径下，单个 300 MiB 文件必然触发那个红框提示（`warnsAboutMemory`：无流式能力
且峰值 > 256 MiB）；SW 路径下 `canStreamToDisk(1, {swStream:true})` 为 true，提示恒不出现。
所以**大文件场景下"点了下载、没弹内存提示、直接开始下载"= 走的是 SW 路径**，这是一条
不需要任何调试工具的可靠判据。
⚠️ **小文件（8 MiB）上这条信号完全无效**：两条路都不会提示。

**S3（大小文件都适用，肉眼可判，不需要调试工具）**：**浏览器下载项出现的时机**。

- SW 路径：`openSwStream` 在**写入第一个字节之前**就把隐藏 iframe 指向 `/__stream__/`，
  浏览器立刻开始一次下载。所以**页面进度还在 0%～个位数百分比时，浏览器的下载条/下载项
  就已经出现了**，然后页面进度和下载进度一起往前走。
- 回落路径：`blobSink` 把整个文件攒在内存里，只在 `close()` 时才 `download(new Blob(...))`。
  所以**浏览器的下载项要等页面跑到 100% 之后才会冒出来**，而且瞬间就完成。

这一条在手机上尤其有用（手机上没有 Network 面板）。判的时候盯着"页面百分比"和
"浏览器下载 UI"两个东西谁先动。

**S4（桌面专用，最直接）**：DevTools → Network，下载开始后应出现一条
`/__stream__/<token>/<文件名>` 的请求，标记为 `(ServiceWorker)`。没有这条请求就是回落。

> 每一项的记录表里都要写清楚**你是靠哪个信号判的分支**。写"看着像成功了"不算。

### 0.4 手机上怎么开调试器

手机各项优先用 S2/S3（不需要工具）。但第 8 项要清 SW、S1 要读 `controller`，还是得连调试器。

**iOS Safari ← Mac Safari（Web Inspector）**

1. **iPhone 上**：设置 → Safari → 划到最底 → 高级 → 打开**「网页检查器」**（Web Inspector）。
2. **Mac 上**：Safari → 菜单栏 Safari → 设置（Settings）→ 高级（Advanced）→ 勾选
   **「显示网页开发者功能」/「在菜单栏中显示"开发"菜单」**（不同版本文案不同，都在
   "高级"面板最底下）。勾上后菜单栏会多出一个**「开发」**菜单。
3. 用**数据线**把 iPhone 连到 Mac。iPhone 解锁，弹出"信任此电脑吗？"点**信任**并输密码。
   （无线调试也行：先连线一次，然后 Mac Safari → 开发 → 你的 iPhone → "通过网络连接"。）
4. iPhone 上用 Safari 打开被测页面（**页面必须开着**，Web Inspector 只能连到活着的标签页）。
5. Mac Safari → **开发** → 菜单里找到**你的 iPhone 名字** → 子菜单里点那个页面的 URL。
   弹出的窗口就是这个页面的 Web Inspector，用法和桌面一样。
6. 在这个 Inspector 的 **Console** 里执行 S1 那条 `navigator.serviceWorker.controller`。

   > 找不到 iPhone 名字：确认第 1、2 步都做了、线连着、iPhone 已解锁、页面开着；
   > 拔插一次数据线；再不行重启 Mac Safari。
   >
   > 「开发」菜单里的 **Service Workers** 分组会单独列出该站点的 SW（点进去是 SW 自己的
   > 控制台，和页面的是两个上下文）。这里能看到 SW 在不在、有没有被回收。
   >
   > ⚠️ iOS 的 Network 面板只记录**页面**发出的请求。`/__stream__/` 是隐藏 iframe 的
   > 导航，**可能不出现在这里**——所以 iOS 上不要把"Network 里没看到"当成回落的证据，
   > 以 S2/S3 为准。

7. **清 SW / 清站点数据（第 8 项要用）**：iPhone 设置 → Safari → 清除历史记录与网站数据
   （会清掉所有站点）；或在 Web Inspector 的 Storage 面板里删该站点的数据。

**安卓 Chrome ← 桌面 Chrome（chrome://inspect）**

1. 手机：设置 → 关于手机 → 连点 7 次"版本号"开开发者选项 → 系统 → 开发者选项 →
   打开 **USB 调试**。
2. 数据线连电脑，手机上"允许 USB 调试吗？"点**允许**。
3. 桌面 Chrome 打开 `chrome://inspect/#devices`，勾上 Discover USB devices，
   等设备和标签页列出来，点那个页面下面的 **inspect**。
4. 弹出的 DevTools 就是完整的桌面 DevTools（有 Console、Network、Application）。
   S1/S4 和清 SW 都在这里做。

**桌面 Safari 的「开发」菜单**同上面第 2 步（第 3 项要用）。

### 0.5 每一项都必须校验内容完整性 —— 以及为什么不能只跑一条 `shasum -c`

**只看"有没有下载下来一个文件"是不够的。** 这条路径上最坏的失败不是报错，而是
"看起来成功但文件被截断 / 混入了别的字节"——用户以为下载好了，几个月后才发现视频放不出来。

而且**下载目录里的同名文件会被浏览器自动改名**：第一次落 `sw-test-big.bin`，第二次就成了
`sw-test-big(1).bin` 或 `sw-test-big-1.bin`。如果你一直对着 `~/Downloads/sw-test-big.bin`
算哈希，那从第二项起你校验的永远是**第一项**留下的那个老文件——每一项都会打 OK，
包括这一项其实下到了一个 index.html 或半截文件的时候。**这正是这份清单唯一存在的理由
（内容错但看着对）上的一个内建假通过。**

所以：**每一项开始前先清空下载目录里的测试文件，结束后对"实际落盘的那一个文件"算哈希。**

把下面两个函数粘进跑测试的那个终端（zsh；每开一个新终端粘一次）：

```zsh
# 每一项【开始前】跑
# 注意 (N) 这个 glob 修饰符不能省：zsh 在没有匹配文件时会直接报 "no matches found"
# 并中止那一行，(N) 让它安静地展开成空。
swreset() { rm -f ~/Downloads/sw-test-*(N); echo "下载目录已清空"; }

# 每一项【结束后】跑，参数是基准文件名：swcheck sw-test-big.bin
swcheck() {
  local want="$1" files got_hash want_hash
  files=(~/Downloads/sw-test-*(N))
  if (( ${#files} != 1 )); then
    echo "FAIL: 期望下载目录里恰好 1 个测试文件，实际 ${#files} 个：${files}"
    echo "      （忘了先跑 swreset？多出来的文件会让判定失效）"
    return 1
  fi
  echo "实际落盘文件：${files[1]}"
  ls -l -- "${files[1]}"
  file -- "${files[1]}"          # 期望 "data"。出现 "HTML document text" 就是漏到 nginx 了
  want_hash=$(awk -v f="/tmp/$want" '$2 == f { print $1 }' /tmp/sw-test-baseline.txt)
  got_hash=$(shasum -a 256 -- "${files[1]}" | awk '{ print $1 }')
  if [[ -n "$want_hash" && "$want_hash" == "$got_hash" ]]; then
    echo "OK 内容与基准一致"
  else
    echo "FAILED 期望 $want_hash"
    echo "       实际 $got_hash"
    return 1
  fi
}
```

`swcheck` 同时钉住三件事：文件**只有一个**（没有拿老文件冒充）、文件**类型是二进制**
（不是被 nginx 兜底的 HTML）、内容**逐字节等于基准**。

手机上没有 shell：把下载好的文件通过 AirDrop（iOS）/ 数据线或 `adb pull`（安卓）传回
Mac 的 `~/Downloads`，**传之前先在 Mac 上跑 `swreset`**，传完再跑 `swcheck`。
**大小相同不代表内容相同**（例如 SW 被换掉后重发了一段，长度可能凑巧对上），必须算哈希。

## 1. 桌面 Chrome —— SW 分支不该抢走原生 Save As

**用哪个文件**：小文件。**分支判定**：S4（这一项要证明的恰恰是"没有 `/__stream__/` 请求"）。

**怎么做**：`swreset` → Chrome 打开小文件链接 → 点"下载并解密" → 在另存为对话框里
保存到 `~/Downloads`，**文件名保持默认** → `swcheck sw-test-small.bin`。

**期望**：弹出系统原生的"另存为"对话框（File System Access API 那条路）。
Network 里**不应**出现 `/__stream__/` 请求。

**怎么判断失败**：
- 没弹对话框、文件直接落进 ~/Downloads，且 Network 里有 `/__stream__/` 请求
  → SW 分支抢走了 Chrome，说明 `pickSaveTarget` 的分支顺序错了（SW 分支必须排在
  `showSaveFilePicker` / `showDirectoryPicker` 两条之后）。
- `swcheck` 不是 OK → 既有的原生路径被这次改动弄坏了（回归，比新功能不工作严重得多）。

## 2. 桌面 Firefox —— 应走 SW 流式

**用哪个文件**：小文件。**分支判定**：S1 + S4（**必做**：8 MiB 上 S2 无效，
两条路都能把一个哈希正确的文件放进下载目录，不看 Network 根本分不出来）。

**怎么做**：`swreset` → Firefox 打开小文件链接 → 开着 DevTools Network → 下载 →
`swcheck sw-test-small.bin`。

**期望**：Network 里有 `(ServiceWorker)` 标记的 `/__stream__/<token>/sw-test-small.bin`；
无"另存为"对话框（Firefox 没有 FSA API）；文件出现在默认下载目录，
文件名是原始文件名（不是 `<token>` 或一串百分号编码）。

**怎么判断失败**：
- **Network 里没有 `/__stream__/`** → 走的是回落路径，这一项**作废**（不是通过也不是
  失败）。先查 S1 的 `controller` 是不是 null，重新注册 SW 后重测。
- **下载到一个 HTML 文件**（`swcheck` 里的 `file` 会打 `HTML document text`，
  或大小只有几十 KB）→ 请求漏到了 nginx 被 `try_files` 兜底成 index.html。
  这是这条路径最危险的失败。
- 文件名变成 `download` 或 token → `Content-Disposition` 没被 SW 交出去。
- 进度条走到 100% 但下载项卡在"正在下载"不收尾 → `close` 回执没收到。
- **`swcheck` 不是 OK → 判定为失败，不管文件大小对不对。**

## 3. 桌面 Safari —— 应走 SW 流式

同第 2 项（小文件，**同样必须用 S4 判分支**，Safari 的 Network 面板在
开发 → 显示网页检查器里，"开发"菜单的开法见 0.4）。

额外注意 Safari 会把下载放进 ~/Downloads 并可能自动解压归档
（Safari 设置 → 通用 → "下载后打开安全的文件"，测试前**关掉它**，否则 .zip/.gz
会被自动展开，你算的就不是下载下来的那个文件的哈希）。

**怎么判断失败**：同第 2 项。另外 Safari 特有的失败形态是"下载项显示完成但文件是 0 字节"
或"文件停在某个中间大小"——这两种都必须算失败并记录当时的文件大小（`swcheck` 会打出来）。

## 4. iOS Safari + 大文件（300 MiB）—— **这一项是整件事的目的**

> **为什么这一项用大文件而不是小文件**：iPhone 上没有可靠的 Network 面板，
> `/__stream__/` 那条 iframe 导航很可能根本不出现在 Web Inspector 里。而 8 MiB 下
> 内存回落路径**同样会**产出一个哈希完全正确的文件——也就是说小文件上这一项
> **无法证明走的是 SW**，一个实际回落了的运行会被打成 ✅，整个第 1 步的结论就是错的。
> 300 MiB 越过 256 MiB 阈值，回落路径**必然**弹内存提示，"没弹提示"于是成为一条
> 不依赖任何工具的充分判据（S2）。小文件的场景保留在第 6 项，作为对照。

**用哪个文件**：**大文件**。**分支判定**：S2（主）+ S3（辅）+ S1（连上 Web Inspector 时）。

**怎么做**：
1. Mac 上 `swreset`。
2. （可选但推荐）按 0.4 把 iPhone 连上 Mac Safari 的 Web Inspector，Console 里跑一次
   `navigator.serviceWorker.controller`，记下是不是非 null。
3. iPhone Safari 打开**大文件**链接（HTTPS）→ 点"下载并解密"。
4. **盯着看**：有没有弹内存提示（红框）？浏览器的下载指示（地址栏旁边的下载箭头 /
   下载列表里出现新条目）是在页面进度还很低的时候出现的，还是等页面跑到 100% 才出现？
   把这两件事记下来 —— 这就是分支判定。
5. 全程**不要切走 app**、不要锁屏（那是第 11 项单独测的场景）。大文件跑一次要几分钟。
6. 下完后在"文件"App 里找到它（iCloud Drive/下载 或 我的 iPhone/下载），
   AirDrop 回 Mac 的 `~/Downloads` → `swcheck sw-test-big.bin`。

**期望**：
- **不出现内存提示**（"你的浏览器不支持流式落盘…"那个红框）。
  → 这就是 S2：出现了就是回落，没出现就是 SW。
- 下载指示在页面进度接近 0% 时就出现（S3）。
- Safari 弹出下载确认（"下载 xxx"），确认后进入"下载项"列表，完成后文件出现在"文件"App。
- 下载过程中 Safari 标签页**不崩溃**（旧路径上 300 MiB 在手机上很可能崩）。
- `swcheck sw-test-big.bin` 打 OK。

**怎么判断失败**（把实际现象**逐字记下来**，这是本步真正的产出）：
- **出现了内存提示** → 走的是回落，SW 分支没生效。先查 S1 的 `controller`；
  controller 非 null 却仍提示 = 下载页没把 `swStream` 开关传给 `canStreamToDisk`（代码 bug）。
  这一项**作废重测**，修好之前拿不到结论。
- 完全没反应 / 只闪一下 → 隐藏 iframe 的导航被 iOS 拦了。
- 打开了一个新页面显示乱码 → `Content-Disposition` 没生效，被当成内联内容渲染。
- 下载项一直转圈不结束 → 流没收尾，或 SW 在后台被回收。
- 标签页被系统回收 / Safari 白屏重载 → 内存没省下来，SW 流没真正生效。
- 下载"完成"但 `swcheck` 报 FAILED（截断 / 内容错）→ **最坏的情况**。
- 下载到 index.html（`file` 打 HTML）→ 漏到 nginx。

**`swcheck` 这一步不能省。** 只要哈希对不上，第 2、3 步就不该做，第 1 步的结论是
"iOS Safari 不行"。

同时记录：iOS 版本、Safari 版本、机型、是否低电量模式、分支是靠哪个信号判的。

## 5. 安卓 Chrome —— 应走 SW 流式

**用哪个文件**：小文件。**分支判定**：S4（**必做**）—— 安卓 Chrome 能用桌面 Chrome 的
`chrome://inspect` 拿到完整 DevTools（见 0.4），所以这里不需要退而求其次。
没有数据线时改用大文件 + S2/S3。

**怎么做**：`swreset` → 按 0.4 连上 chrome://inspect → 安卓 Chrome 打开小文件链接（HTTPS）
→ 下载 → `adb pull /sdcard/Download/sw-test-small.bin ~/Downloads/`（或数据线拷）
→ `swcheck sw-test-small.bin`。

**期望**：Network 里有 `(ServiceWorker)` 的 `/__stream__/` 请求；进入 Chrome 的下载列表，
完成后在 `Download/` 目录里。

**怎么判断失败**：同第 2 项。安卓 Chrome 特有的一点：移动版 Chrome **不提供** FSA API
（没有 `showSaveFilePicker`），所以这里应当走 SW 分支。
如果 Network 里没有 `/__stream__/` 请求，先确认 `navigator.serviceWorker.controller`
非 null，再判定 —— 判不出分支就是作废，不是通过。

## 6. iOS Safari + 小文件（8 MiB）—— 短下载路径的对照组

这一项**不是**决策依据（决策看第 4 项），它是第 4 项的对照：确认"短下载"这条最常见的
真实用法在 iOS 上也走得通，以及在第 4 项失败时判断"是不是只有大文件不行"。

**用哪个文件**：小文件。**分支判定**：⚠️ **这一项靠自己分不出分支**——8 MiB 下 S2 无效
（两条路都不提示），哈希两条路也都对。**必须**用其中一个：
- S3：盯下载指示出现的时机（SW = 页面还没到 100% 就出现；回落 = 100% 之后才出现）。
  8 MiB 很快，要**提前盯着**，一眨眼就过去了。
- 或按 0.4 连 Web Inspector，下载前确认 `navigator.serviceWorker.controller` 非 null，
  并在开发 → Service Workers 里确认 SW 活着。

两个都判不出来的话，这一项记 **"分支未知"**，不要记 ✅。

**怎么做**：`swreset` → iPhone Safari 打开小文件链接 → 下载 → AirDrop 回 Mac →
`swcheck sw-test-small.bin`。

**期望**：Safari 弹下载确认 → 下载项完成 → 文件在"文件"App → `swcheck` 打 OK。

**怎么判断失败**：同第 4 项那张失败清单（去掉内存提示相关的两条）。

## 7. 中途取消下载 —— 页面必须报错，不能卡死或静默失败

**用哪个文件**：**大文件**（小文件下完得太快，来不及取消；而且大文件下这一项自带
S2 分支判定）。**分支判定**：S2 —— 没弹内存提示才说明走的是 SW；
弹了提示就说明是回落，而**回落路径下这一项根本不成立**（blobSink 的下载是在内存攒完
之后一瞬间的事，取消它页面毫无感知，会照常显示"完成"）。**看到页面显示成功完成，
就是走了回落，作废重测。**

**怎么做**：`swreset` → 桌面 Firefox 或 Safari 上开始下载**大文件**，确认没弹内存提示、
下载项在低百分比时就出现了 → 在浏览器的下载界面里点"取消"（×）→ 盯着页面。

**期望**（下面两种**都算符合期望**，但必须记录实际是哪一种）：

- **(A) `cancelled` 文案**：页面几秒内进入错误态，显示
  **"下载已取消，文件未保存。可以重新开始下载。"**
  —— 浏览器把取消传成了 SW 的 `cancel`，SW 转告页面，归因最精确。
- **(B) `swFail` 文案**：页面显示**"保存到磁盘时中断：请重试。"**，
  且是在取消之后**最多约 60 秒**出现的。
  —— 部分浏览器取消下载时**不触发** SW 的 `cancel` 事件，只是消费方不再 pull；
  页面侧要等 `STREAM_ACK_TIMEOUT_MS`（60s）判死才报错。这**同样是诚实的归因**
  （字节没错、只是没交到磁盘）且同样可重试，属于可接受结果。

两种情况下都必须有**重试按钮**，点它能重新开始一次完整的下载
（`swreset` 后再 `swcheck` 校验一次）。

**怎么判断失败**：
- 页面停在某个百分比一动不动**超过 90 秒**（给 60s 超时留足余量）→ 取消信号既没传回
  页面、停滞超时也没生效，`write()` 挂死了。
- 显示"解密失败：密钥错误或文件已损坏" → **归因错了**。用户被告知文件坏了，
  其实只是他自己点了取消。
- 显示错误但没有重试按钮 → 用户走进死胡同。
- 页面显示下载**成功完成** → 见上面"分支判定"，多半是走了回落，作废重测。

**记录**：是 (A) 还是 (B)，以及从点取消到页面报错之间隔了多久。

## 8. 首次访问（SW 刚注册、可能还没 claim）—— 绝不能下载到一个 HTML 文件

这是这条路径上后果最严重的失败：请求漏到 nginx，`try_files` 兜底返回 index.html，
用户拿到一个扩展名正确、内容是网页的文件。

**用哪个文件**：**大文件**（这样 S2 能告诉你这一次到底是走了 SW 还是干净回落——
这一项两种都算通过，但**必须记录是哪一种**，否则等于什么都没测到）。

**怎么做**（必须清干净 SW 才能复现）：
1. `swreset`。
2. DevTools → Application → Service Workers → **Unregister**；
   Application → Storage → **Clear site data**（勾上 unregister service workers）。
3. 关掉所有该站点的标签页。
4. 重新打开下载链接，**立刻**（页面一出现就）点"下载并解密"，不要等。
5. `swcheck sw-test-big.bin`。
6. Firefox / Safari 上重复（Firefox: 设置 → 隐私与安全 → Cookie 和网站数据 → 清除数据）。

**期望**（两种都可以接受，记录实际是哪一种）：
- **(A) 走 SW 流式并拿到完整文件**（没弹内存提示，`swcheck` OK）。
- **(B) 干净回落到旧的内存路径**（弹了内存提示，点"仍要下载"后 `swcheck` OK）。

**怎么判断失败**：
- `swcheck` 里 `file` 打出 `HTML document text` / `head -c 200` 看到 `<!doctype html>`
  → **严重失败**。说明 `swStreamReady()` 在 SW 还没 claim 时错误地返回了 true。
- 下载下来一个 0 字节文件（`swcheck` 的 `ls -l` 会露出来）。
- 页面报错。

## 9. "每次都问我保存到哪"对话框开着超过 60 秒

**用哪个文件**：**大文件**（S2 是这一项唯一的分支判据：如果走了回落，结果 (A)
"下载正常完成"和 SW 路径下的 (A) 长得**一模一样**，会给出假通过）。
**分支判定**：S2 —— 弹了内存提示就是回落，作废重测；另外桌面上顺手用 S4 双确认。

**背景**：页面侧每一次 ack 等待有 60 秒停滞上限（`STREAM_ACK_TIMEOUT_MS`）。浏览器的
"总是询问保存位置"对话框会挡住消费方的 pull，ack 因此不来。

**怎么做**：`swreset` → Firefox → 设置 → 常规 → 下载 → 勾选"总是询问你要保存文件的位置"。
开始下载**大文件**，确认没弹内存提示，弹出保存对话框后**放着不动 90 秒**，
再选 `~/Downloads` 确认 → `swcheck sw-test-big.bin`。

**期望**（记录实际现象，两种都算合法结果，但要写清楚是哪一种）：
- (A) 下载正常完成，`swcheck` OK —— 说明对话框期间浏览器仍在 pull（对话框在响应体开始
  传输之前弹出，此时流还没被消费）。
- (B) 页面在 60 秒后报错"保存到磁盘时中断：请重试。"，下载失败 —— 已知取舍，可接受，
  但要记进结论，因为这会影响开着这个选项的用户。

**怎么判断失败**（真正的失败，区别于上面两种）：
- 页面无声无息停在某个百分比，**既不完成也不报错**，超过 3 分钟 → 停滞超时没生效。
- 下载"完成"但 `swcheck` FAILED → 最坏情况。

**测完把那个"总是询问保存位置"的勾去掉**，否则后面各项都会被这个对话框干扰。

## 10. 下载中途暂停超过 60 秒

**用哪个文件**：**大文件**（同第 9 项：小文件下暂停都来不及点，而且 (A) 分不出分支）。
**分支判定**：S2 + S4。

**怎么做**：`swreset` → 开始下载大文件，确认没弹内存提示 → 在浏览器下载界面里点"暂停"，
等 90 秒，再点"继续" → `swcheck sw-test-big.bin`。

**期望**（同样两种合法结果，记录实际是哪一种）：
- (A) 恢复后继续下载并完成，`swcheck` OK。
- (B) 页面报错"保存到磁盘时中断：请重试。"，且有重试按钮 —— 已知取舍
  （`STREAM_ACK_TIMEOUT_MS` 的注释里明确写了这一条），可接受。

**怎么判断失败**：
- 页面永久挂在某个百分比不报错（超过 3 分钟）。
- 恢复后下载"完成"但 `swcheck` FAILED（丢了中间一段）—— **严重**。

## 11. 手机上切到别的 app 再切回来（定时器被节流）

**用哪个文件**：**大文件**（既为了留出足够的下载时间，也因为 S2 是手机上唯一
不需要工具的分支判据）。**分支判定**：S2 + S3。

**背景**：页面靠 10 秒一次的 `stream-ping` 心跳把 SW 拉住不让它被回收。手机上标签页
进入后台后 `setInterval` 会被大幅节流甚至暂停，心跳可能停发 → SW 被回收 → 注册表蒸发。
这是手机上最可能发生的失败方式，也是这份清单里最重要的一项（仅次于第 4 项）。

**怎么做**：`swreset` → iOS Safari（以及安卓 Chrome）上开始下载**大文件**，
确认没弹内存提示 → 5 秒后按 Home 切到别的 app（或锁屏），停留 **2 分钟**，
再切回 Safari → AirDrop 回 Mac → `swcheck sw-test-big.bin`。

**期望**（记录实际是哪一种）：
- (A) 下载在后台继续并完成，`swcheck` OK —— 最好的结果，记 ✅。
- (B) 切回后页面显示"保存到磁盘时中断：请重试。"并有重试按钮 —— 可接受的失败：
  用户知道发生了什么，也知道怎么办。记 ❌（见下面决策规则）。
- (C) 下载在后台**完成了**（`swcheck` OK），但页面切回后仍显示"正在下载 x%" ——
  字节是对的，UI 状态不一致。记 **⚠️**（见下面决策规则）。

**怎么判断失败**：
- 切回后页面永久停在某个百分比，既不完成也不报错，**且文件也没下完** → 失败。
  （注意和 (C) 区分：(C) 的判据是**文件已经完整落盘**，页面只是没更新。
  所以看到"页面停在 x%"时，**先去检查文件在不在、`swcheck` 过不过**，再决定记 (C) 还是失败。）
- 下载显示完成但 `swcheck` FAILED（被截断）→ **最坏情况**，必须记录并让第 2、3 步停下来。

如果这一项在 iOS 上稳定失败，即使第 4 项（前台下载）通过，这个功能对手机用户
也只在"不切走"的窄场景里有效，结论里必须写明这个限制。

### 决策规则

**第 11 项的 (C) 怎么算**：(C)（后台下载完成、UI 停在 x%）在下面的规则里
**按 ❌ 处理**（即不做第 3 步），但它**不阻断第 2 步**——字节是完整的，问题纯在 UI 状态。
同时开一条 followup：页面在被节流后要能重新同步进度/收尾状态。

**主规则（保守）**：第 4 项与第 11 项都拿到 ✅ 才建议做第 2 步（流式 ZIP）。

- 第 4 项 ❌ → 这条路对 iOS 无效，应当回到"提示用户换浏览器 / 用 CLI"的方案。
- 第 4 项 ✅ 但第 11 项 ❌ 或 (C) → 功能可以留着（比现状好），但**不要**在第 3 步把
  实时接收路也切过来 —— 那条路的传输时间更长，切后台的概率更高。

**这条主规则偏严，这是刻意的取舍，但要知道自己在放弃什么**：流式 ZIP（第 2 步）
对**桌面 Firefox / Safari** 有**独立于 iOS 的价值**——那两个浏览器今天在多文件下载上
必须把整个 ZIP 攒进内存（`memoryPeakBytes` 里的 2× 峰值），流式 ZIP 直接解决这个问题，
和第 4 项的结论没有任何依赖关系。

所以：第 4 项 ❌ 时，**默认停下来**（少做一件事的代价小于在一条走不通的路上继续投入），
但如果第 2、3 项（桌面 Firefox/Safari）都 ✅，可以把"只面向桌面的流式 ZIP"作为一个
**独立的、缩小范围的**提案重新评估，而不是直接判死。这个决定交给人，不由这张表自动得出。
