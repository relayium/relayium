# 设计方案：存储下载去中央化（Direct-from-Node）

状态：**提案（待决策）** · 作者：Relayium · 关联 bug：own-node 下载免流量（已由 A+B 修复，见 `c9c89f1`）

---

## 1. 要解决的问题

当前**存储模式**（云端异步 up/down、`/d/` 分享链接）的所有 blob 下载都经中央代理转发：

```
自建/机队节点  ──①中央抓取──▶  中央服务器  ──②转发──▶  下载者
              (节点→中央)                  (中央→客户端，出口带宽)
```

代码路径：`handleFileBlob`（`files.go`）→ `blobFor` 返回 `RemoteBlobStore` → `bs.GetRange()`（中央向节点发 HTTP 抓密文，`storage/remote.go`）→ `io.Copy(w, rc)`（中央把密文吐给客户端）。**每次下载文件都穿过中央两趟，且无缓存**。

后果：

- 分布式存储节点只卸载了**磁盘**，没卸载**下载带宽**。中央出口带宽 ≈ 所有存储文件下载量之和。
- 用户规模上来后，中央这条出口管子是硬瓶颈，**加节点救不了下载带宽**。
- per-plan 流量帽只是把这笔带宽账变得"有界+可计费"，不等于横向扩展——中央的管子还得随业务一起变粗、变贵。

> 对比：**实时模式**（配对码/分享链接直传）数据走 P2P 或 TURN 中继节点，**不过中央**，本来就横向扩展。这个提案只针对存储模式。

## 2. 目标 / 非目标

**目标**
- 让存储下载的带宽分摊到各存储节点，中央退出数据面，只承载控制面（几百字节的鉴权+重定向）。
- 保持零知识：节点只见密文，解密密钥始终只在 URL fragment（`#k=`），不经任何服务器。
- 保持现有下载语义：TTL / 阅后即焚（burn）/ 下载次数上限（max-downloads）/ per-plan 流量计量，全部继续正确。

**非目标**
- 不改实时模式（已经是去中央化的）。
- 不改上传路径（上传可以继续经中央，或另议；本提案聚焦下载）。
- 不引入 CDN 作为主方案（一次性、唯一密文 + burn 语义，缓存命中率极低，CDN 帮不上）。

## 3. 提案架构：签名令牌 + 直连节点（presigned direct download）

思路类比 S3 presigned URL：中央做鉴权和记账，把**数据传输**交给节点。

```
下载者 ──①GET /api/files/{id}/dl──▶ 中央（鉴权/claim slot/计量预扣/签令牌）
下载者 ◀──②302 或 JSON: https://node.example/blob/{key}?t=<签名令牌>── 中央
下载者 ──③GET 直连节点，带令牌──▶ 存储节点（校验令牌→吐密文）
                                    节点↔客户端直连，中央不在数据面
下载者 ──④(可选)完成回执──▶ 节点 ──上报egress/完成──▶ 中央（对账）
```

### 3.1 控制面（中央）

新增一个轻端点，比如 `GET /api/files/{id}/dl`（沿用现有公共、零知识约定，不读下载者身份）。它做现在 `handleFileBlob` 里除了 `io.Copy` 之外的所有事：

1. `liveFile` 校验存在/未过期。
2. 下载限速（复用刚加的 `downloadLimiter`）。
3. **流量闸**：`overTraffic(owner, size)`，超额 429。
4. **限量文件**：`ClaimDownloadSlot`（阅后即焚/max-downloads）——**在签发令牌前原子占坑**。
5. **计量预扣**：`RecordMeter(owner, MeterDownload, size)`——按整文件大小**预先**记账（下载失败再对账退回，见 §4.2）。
6. 若文件在节点上且该节点**支持直连**：签发一个短时效令牌（§3.3），返回 `302`（或 JSON `{url, token}` 供 SW/CLI 用 fetch）。
7. 否则（节点不支持直连 / 离线 / 文件在中央本地）：**回落到现有代理路径**`handleFileBlob`。

### 3.2 数据面（节点）

节点新增一个面向公网的下载端点 `GET /blob/{key}?t=<token>`：

- 校验令牌签名、未过期、`key` 与令牌绑定。
- 直接把密文流给客户端，支持 `Range`（断点续传）。
- 只见密文，不解密、不认识用户。
- 需要：公网可达、自己的 TLS 证书、CORS（允许浏览器跨源 fetch 到 `relayium.com` 发起的下载）。

### 3.3 令牌设计

短时效（如 60–120s）、单文件绑定、防篡改。最简：中央和节点共享一个 per-node 密钥（节点注册时已有 `StorageSecret`），令牌 = `HMAC(nodeSecret, key ‖ exp ‖ nonce)`：

```
t = base64url(exp ‖ nonce ‖ HMAC-SHA256(nodeSecret, "dl" ‖ key ‖ exp ‖ nonce))
```

- 节点用同一个 `nodeSecret` 验签，无需回中央。
- `exp` 短，令牌泄露窗口小。
- `nonce` 让同一文件的多次下载令牌不同（利于节点侧做一次性/审计，可选）。
- 不放用户信息 → 零知识不受影响。

> 进阶（可选）：非对称签名（中央私钥签、节点用中央公钥验），这样节点即便被攻破也签不出有效下载令牌，且能支持"任意节点验任意中央令牌"。代价是密钥分发复杂一点。

## 4. 难点与对策

去中央化后，"中央在数据面顺便做的事"要重新安排。

### 4.1 阅后即焚 / 下载次数（burn / max-downloads）

现状是中央在 `io.Copy` 成功后才 `deleteFile`/`bump count`，用的是"这次请求实际发了多少字节"来判定。去中央化后中央看不到传输结果。

**对策：签令牌时就 claim（预占），失败靠对账回滚。**
- 令牌签发前 `ClaimDownloadSlot`（已是原子 `UPDATE ... WHERE count < max RETURNING`）。占不到就不发令牌。
- 需要节点**回执**才能知道下载是否真完成：
  - **乐观**：签了令牌就当这一次用掉。简单，但"签了令牌却没下成"会白白消耗一次配额——对 burn 文件尤其不友好。
  - **回执对账**（推荐）：节点在下载完成/失败后异步回调中央（带令牌 nonce + 传输字节数），中央据此确认扣减或 `ReleaseDownloadSlot` 退回。回执丢失用 TTL 兜底（令牌过期即视为已用或按策略退回）。
- burn 文件的物理删除：中央在确认最后一次下载完成后，指令节点 `DELETE /blob/{key}`（已有 Delete 接口）。

### 4.2 流量计量（per-plan traffic）

现状按 `io.Copy` 实发字节记 `RecordMeter`。去中央化后中央不经手字节。

**对策：预扣 + 回执对账。**
- 签令牌时按整文件大小**预扣**（保证流量闸不被绕过）。
- 节点回执带实际 egress 字节 → 中央按差额对账（断点续传/未下完的多退少补）。
- 回执缺失：保留预扣（宁可略微多算，不可漏算——和现有"宁可多计不可漏计"的取向一致）。

### 4.3 断点续传 / Range

- 节点端点原生支持 `Range`（比现在中央代理还简单，少一跳）。
- 计量对账用回执里的实际字节，天然处理 resume（和现在 `n != sf.Size` 的逻辑同源）。

### 4.4 节点离线 / 不支持直连

- 中央在 §3.1 第 6 步判断：节点 `LastSeenAt` 新鲜 + 标记了"公网可直连" + 有 TLS 才走直连。
- 否则**回落到现有代理路径**。所以这是**渐进增强**：不支持直连的节点（老节点、纯内网 BYO 节点）行为完全不变。

### 4.5 零知识 / 隐私

- 密文 + fragment 密钥的模型不变：节点只见密文，`#k=` 不上任何服务器。
- **新增暴露面**：下载 URL 里出现节点地址。属主的节点地址对下载者可见了（当前是全藏在 `relayium.com` 背后）。
  - 缓解：令牌短时效 + 节点侧只认令牌，不暴露除"这台机器存了某个密文块"以外的信息。
  - 对 BYO 节点用户要**明确告知**："开启公网直连下载会暴露你节点的地址给下载者"，并做成**可选开关**（默认关，隐私优先）。

### 4.6 节点侧运维门槛

直连要求节点公网可达 + TLS + CORS，比现在"只要能连中央"高一档。

- 机队（fleet）节点：我们自己运维，直接满足。**首批只对机队节点开直连**，收益最大、风险最小。
- BYO 用户节点：作为进阶可选项，提供 Caddy/自动 TLS 的一键配置；不满足的就继续走代理。

## 5. 与其他方案对比

| 维度 | 现状（全代理） | C：直连节点 | CDN 前置 |
|---|---|---|---|
| 中央下载带宽 | O(全部下载量) | O(控制面，几乎为0) | O(未命中量) |
| 横向扩展 | ❌ | ✅（随节点扩） | 部分 |
| 零知识 | ✅ | ✅ | ✅ |
| 隐私（节点地址） | 全隐藏 | 下载者可见（可选开关缓解） | 全隐藏 |
| 节点运维门槛 | 低（只连中央） | 高（公网+TLS+CORS） | 低 |
| burn/次数/计量 | 中央一处，简单 | 需预扣+回执对账 | 同现状（仍代理）或复杂 |
| 一次性密文缓存收益 | — | — | ❌ 命中率极低 |

CDN 对"唯一密文 + burn"基本无效，排除为主方案；可作为多下载热门链接的补充，非本提案重点。

## 6. 分阶段落地

1. **P0 — 令牌与节点直连端点（仅机队）**：节点加 `GET /blob/{key}?t=`，中央加 `/api/files/{id}/dl` 返回 302；只对机队节点启用；burn/次数用**乐观 claim**先跑通；计量用**预扣**。回落到代理保底。
2. **P1 — 回执对账**：节点异步回执（字节数/完成态），中央对账 `RecordMeter` 差额与 `ReleaseDownloadSlot`；令牌 TTL 兜底。
3. **P2 — BYO 节点可选直连**：加"公网直连"节点开关 + 用户告知 + 一键 TLS 配置文档；不满足者继续代理。
4. **P3 — 硬化**：非对称令牌签名、节点侧一次性 nonce/审计、SW 流式下载改走直连 URL、CLI `down` 走直连。

每一阶段都可独立上线、可回退（关开关即回代理）。

## 7. 待你决策的关键点

1. **要不要做**：取决于对存储模式未来规模的预期。现在用户量小、A+B 已经让成本"有界且可计费"，可以先不做；如果判断存储下载会成为主力，这是迟早要立项的。
2. **隐私 vs. 带宽**：直连会把节点地址暴露给下载者。机队节点无所谓；BYO 节点必须做成默认关的可选开关。你接受这个取舍吗？
3. **burn/次数的严格度**：乐观 claim（简单，签了令牌就算用一次）vs. 回执对账（准确，但要节点回调 + 兜底）。P0 想先用哪个？
4. **范围**：先只做机队节点直连（低风险、收益大），还是一开始就把 BYO 直连一起做？

我的建议：**先只对机队节点做 P0（乐观 claim + 预扣计量 + 代理保底）**，用最小改动验证"中央退出数据面"这条路，再按数据决定要不要推进 P1–P3 和 BYO 直连。
